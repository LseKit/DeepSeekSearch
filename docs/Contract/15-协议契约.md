## 二、传输模式：单档 stateless（不加 mode 字段）

### 2.1 SDK 语义（go-sdk v1.8.0 源码注释原文）

> The streamable HTTP transport supports every legacy SDK protocol version, but the SEP-2575 >= 2026-07-28 protocol is **only supported when the transport is configured as stateless**.

| `Stateless` | 2026-07-28 | 2025-11-25 及更早 | 结果 |
|:-:|:-:|:-:|---|
| **`true`** | ✅ | ✅ | **超集，两者通吃** |
| `false` | ❌ 回 `-32022` | ✅ | 只剩 legacy |

**结论：默认且唯一取 `true`。** 配 `false` 不会让任何客户端变得可用，只会砍掉 2026-07-28。

### 2.2 实测：legacy 客户端在 stateless 端点上的完整轨迹

```
POST /mcp  MCP-Protocol-Version: ""          → 200   (initialize, 无版本头视为 legacy)
GET  /mcp  MCP-Protocol-Version: 2025-11-25  → 405   (老客户端会试 GET 流, 被拒)
POST /mcp  MCP-Protocol-Version: 2025-11-25  → 202   (notifications/initialized, 无 body)
POST /mcp  MCP-Protocol-Version: 2025-11-25  → 200   (tools/list)
POST /mcp  MCP-Protocol-Version: 2025-11-25  → 200   (tools/call)
```

🔴 **关键：老客户端拿到 GET 405 之后不会中断，继续走 POST 正常完成。单档 stateless 不损失老客户端。**

### 2.3 SDK 客户端 5 组场景实测结果

| 客户端 | 端点 | 协商版本 | tools/list | tools/call |
|---|---|:-:|:-:|:-:|
| modern | `/mcp` (stateless) | **2026-07-28** | 1 | ✅ |
| legacy 2025-11-25 | `/mcp` (stateless) | 2025-11-25 | 1 | ✅ |
| legacy 2024-11-05 | `/mcp` (stateless) | 2024-11-05 | 1 | ✅ |
| modern | `/mcp/session` (stateful) | 2025-11-25（自动降级） | 1 | ✅ |
| legacy 2025-11-25 | `/mcp/session` (stateful) | 2025-11-25 | 1 | ✅ |

Mcp-Method: server/discover

### 3.2 实测响应（HTTP 200）

## 四、必需的 HTTP 头与校验

| 头 | 何时必需 | 缺失/不匹配的实测响应 |
|---|---|---|
| `MCP-Protocol-Version` | 所有 2026-07-28 请求 | 无头 → 走 legacy 路径（200）；不支持的版本 → **text/plain 400** |
| `Mcp-Method` | **所有请求** | `400` `{"code":-32020,"message":"missing required Mcp-Method header"}` |
| `Mcp-Name` | `tools/call` / `resources/read` / `prompts/get` | `400`（`tools/call` 缺此头实测 400） |
| `_meta.protocolVersion`（body 内） | 所有 2026-07-28 请求 | `400` `{"code":-32602,"message":"missing or invalid _meta field \"io.modelcontextprotocol/protocolVersion\""}` |

### 4.1 头体一致性

```
Mcp-Name: wrong   +   body {"name":"echo"}
→ 400 {"code":-32020,"message":"header mismatch: Mcp-Name header value 'wrong' does not match body value 'echo'"}
```

### 4.2 不支持的版本（注意：不是 JSON-RPC 错误）

```
MCP-Protocol-Version: 1999-01-01
→ HTTP 400
   Content-Type: text/plain; charset=utf-8
   Bad Request: Unsupported protocol version (supported versions: 2026-07-28,2025-11-25,2025-06-18,2025-03-26,2024-11-05)
```

🔴 **这是纯文本，不是 JSON-RPC `-32022`。** 客户端若按 JSON 解析会崩。我们的测试必须断言 `Content-Type` 是 `text/plain`。

### 4.3 未知方法

```
Mcp-Method: tools/bogus
→ HTTP 404
   {"jsonrpc":"2.0","id":4,"error":{"code":-32601,"message":"JSON RPC not handled: \"tools/bogus\" unsupported"}}
```

### 4.4 `initialize`（2026-07-28 已移除）

| 场景 | 实测 |
|---|---|
| 带 `_meta` 的 initialize（有 `MCP-Protocol-Version: 2026-07-28`） | `400` `-32602` missing `_meta.protocolVersion`（因为 `params._meta` 位置不对） |
| 不带 `_meta` 的 initialize（legacy 路径） | `200`，回显客户端请求的 `protocolVersion` |

legacy 四版本握手实测（全部 200 并回显各自版本）：

| 请求 `protocolVersion` | 响应 `protocolVersion` |
|---|---|
| 2024-11-05 | 2024-11-05 |
| 2025-03-26 | 2025-03-26 |
| 2025-06-18 | 2025-06-18 |
| 2025-11-25 | 2025-11-25 |

### 4.5 通知

```
POST /mcp  {"jsonrpc":"2.0","method":"notifications/initialized"}
→ HTTP 202, body 长度 0
```

## 六、必须自己补的三件事（SDK 默认不做）

### 6.1 Origin 校验（实测 SDK 默认缺失）

```
POST /mcp  Origin: https://evil.example.com  →  HTTP 200   🔴
```

**必须自己加**：

```go
handler := mcp.NewStreamableHTTPHandler(getServer, opts)
protection := http.NewCrossOriginProtection()
protected := protection.Handler(handler)
```

配置项：`server.http.enable_cross_origin_protection = true`（默认）、`allowed_origins = []`。

### 6.2 `ttlMs` 与 `cacheScope`（默认 0 = 没缓存）

`SetCacheable` 是**服务器级**的单个回调，所以它 MUST 自己按 URI 分派 —— 🔴 **MUST NOT 对所有请求返回同一组值**：

```go
srv := mcp.NewServer(impl, &mcp.ServerOptions{
    SetCacheable: func(_ context.Context, r mcp.Request, c *mcp.Cacheable) {
        // go-sdk v1.8.0 的 mcp.Request 没有 URI()；由 tools.CacheableForRequest
        // 从 resources/read 的 Params.URI 取键，其余请求回落到 (1000,"private")。
        // 取值表在 internal/tools，与 14-错误契约 §五 逐字一致，MUST NOT 在这里再抄一份。
        c.TTLMs, c.CacheScope = tools.CacheableForRequest(r)
    },
})
```

| URI | `ttlMs` | `cacheScope` |
|---|:-:|:-:|
| `ds://effective-config` | `300000` | `private` |
| `ds://error-codes` | `300000` | `public` |
| `ds://usage` | `1000` | `private` |

🔴 **为什么原设计「一个回调返回 300000/public」是错的**：那样 `ds://usage` 也会被客户端缓存 5 分钟 —— 而它是**每次调用都在变**的用量统计，缓存 5 分钟等于统计数字直接失去意义（模型会拿着 5 分钟前的 `calls` 数做判断）。同时 `effective-config` 含脱敏配置与 `config_sha256`，标成 `public` 意味着允许进**共享**缓存。

实测：不设此回调时 `ttlMs` 为 0，客户端缓存毫无收益。

> 🔴 **`ttlMs` MUST NOT 为 0**，易变的用 `1000`。理由：0 同时表示「我故意不缓存」与「`SetCacheable` 回调忘了接」—— 后者正是上面那个「缓存毫无收益」的静默故障。用 `1000` 表示不缓存，0 就重新变成**只可能是 bug** 的信号，§四 的 P2 断言（`ttlMs > 0`）也才有意义。完整裁决见 `14-错误契约` §5.0 第 3 条。

### 6.3 中间件的 `Flush` / `Unwrap`（踩过的坑，必读）

**症状**：给 handler 套日志中间件后，stateful 端点的 GET SSE 流彻底卡死 —— `curl` 3 秒收到 **0 字节**、HTTP=000；SDK 客户端连接 **hang 满 3 分钟**，且**没有任何错误日志**。

**根因**：中间件的 `statusWriter` 只嵌入了 `http.ResponseWriter` **接口**，而该接口**不含 `Flush`** —— 嵌入接口不会提升方法。于是 `w.(http.Flusher)` 类型断言失败，SSE 永不 flush。

**修法（MUST 逐字使用）**：

```go
type statusWriter struct {
    http.ResponseWriter
    code int
}

func (s *statusWriter) WriteHeader(c int) { s.code = c; s.ResponseWriter.WriteHeader(c) }

// Flush 转发给底层 writer，保证 SSE 首包立即下发。
// 少了这个方法，整个流会静默卡死且不报错。
func (s *statusWriter) Flush() {
    if f, ok := s.ResponseWriter.(http.Flusher); ok {
        f.Flush()
    }
}

// Unwrap 供 http.ResponseController 逐层解包。
func (s *statusWriter) Unwrap() http.ResponseWriter { return s.ResponseWriter }
```

**这条写进 `Engineering/20-编码规范.md` 的禁止项**：任何包装 `http.ResponseWriter` 的中间件 MUST 实现 `Flusher` + `Unwrap()`。

## 六之二、中间件链顺序（wire 级后果，MUST NOT 调换）

🔴 **钉死的顺序**：

```
recover → accessLog → securityHeaders → healthz → pathGuard → admission → crossOrigin → hostGuard → authGuard → bodyLimit → mcp
```

`Contract/11-接口契约.md` §6.2 是这条链的装配视图，两处 MUST 一致。

### 为什么 `crossOrigin` 必须在 `hostGuard` / `authGuard` **之外**

原设计把 `crossOrigin` 放在 `authGuard` **之内**（`… hostGuard → authGuard → crossOrigin → bodyLimit …`）。按 CORS 规范这会让 `auth_enabled=true` 时**任何浏览器端 MCP 客户端都不可用**：

| # | 后果 | 依据 |
|:-:|---|---|
| 1 | preflight 的 `OPTIONS` 请求**不携带 `Authorization`**（浏览器只发 `Origin`、`Access-Control-Request-Method`、`Access-Control-Request-Headers`）。`crossOrigin` 在 `authGuard` 之内 ⇒ preflight 先吃 `401`（`3091`），`Access-Control-Allow-*` 头永远发不出去 ⇒ 浏览器判 CORS 失败，真正的 `POST` 根本不会发出 | Fetch 标准 §4.8 preflight；`14-错误契约.md` `3091` |
| 2 | 即便是简单请求，`authGuard` 的 `401` / `hostGuard` 的 `403` 响应也**不带 CORS 头** ⇒ 跨源响应「无 CORS 头 = 对 JS 不可读」，客户端只看到 `TypeError: Failed to fetch`，拿不到 `3091`/`3093` 错误体 ⇒ 用户无法区分「token 写错了」和「服务挂了」 | 同上 |
| 3 | 跨源页面可以拿 `authGuard` 当 token 探测器（`401` vs `200`），而 `crossOrigin` 本该在它之前就把请求拒掉 | `13-配置契约.md` §3.1：`enable_cross_origin_protection` 的定位就是「防止恶意网页通过浏览器调用你的本地工具」 |

**为什么选「把 `crossOrigin` 提出来」而不是「让 `authGuard` 放行 `OPTIONS`」**：本端点根本不接受 `OPTIONS` —— §五 实测 `GET /mcp` 与 `DELETE /mcp` 都是 `405 Allow: POST`。在鉴权层为 `OPTIONS` 开例外，等于在**最敏感的中间件**里引入一条无人定义语义的路径，而 `Access-Control-Allow-*` 头仍然由 `crossOrigin` 发 ⇒ 顺序问题一点没解决，只是把 `401` 换成了一个更含糊的响应。提到外面则三条后果一并消失。

**为什么 `healthz` 仍在 `crossOrigin` 之外**：探活必须能被 systemd / nginx / 监控**匿名且带公网 Host** 调用（§七之三「不鉴权」）。这些调用方不发 `Origin` 头，本来也不会被 `crossOrigin` 拦；把它留在最外是为了让反代转发公网 `Host` 时探活仍然可用（`hostGuard` 在 `healthz` 之后）。

**本项目支持浏览器客户端吗**：**支持**。判据是 `13-配置契约.md` §二 存在 `server.http.allowed_origins` 这个键，其文档原文是「你在浏览器里有个自建面板要直接调这个 MCP，才需要把面板地址加进来」。既然配置层承诺了这个场景，传输层 MUST 让 preflight 走得通 —— 否则那个键就是孤儿配置（`respect_retry_after` 的教训，见 `23-上游能力实测报告.md` §6.3）。

### 验收

顺序由 `Tasks/Task-11-Transport与架构守护.md` A-02 的 `TestMiddlewareOrder`（全等比较装配序列）与 **P15 的第 ② 个子断言**（`OPTIONS` preflight 不带 `Authorization` 时 MUST NOT `401`）共同强制。

## 七、响应形态：`JSONResponse`

| `json_response` | Content-Type | 适用 |
|---|---|---|
| **`true`（默认）** | `application/json` | 一次请求一次回包，解析开销小 |
| `false` | `text/event-stream` | 兼容只认 SSE 的旧客户端 |

实测：`JSONResponse: true` 下，modern 与 legacy 请求**都返回 `application/json`**，GET 仍 405。

```
POST /mcp/json  (modern, tools/list)
→ 200  Content-Type: application/json
   {"jsonrpc":"2.0","id":1,"result":{"resultType":"complete",...}}

POST /mcp/json  (legacy initialize 2024-11-05)
→ 200  Content-Type: application/json
   {"jsonrpc":"2.0","id":2,"result":{"protocolVersion":"2024-11-05",...}}
```

**建议默认 `true`**：搜索/Fetch 都是一次请求一次回包，用不着流。

> 🔴 **默认 `true` 的一个副作用：SSE 路径在默认配置下永远跑不到**。§6.3 那个「少一次 `Flush` 就静默卡死 3 分钟」的坑只存在于 `text/event-stream` 形态下，而默认配置根本不产生 SSE 流 ⇒ 验收断言 **P18** 若跟着默认配置跑，就是一个**永不执行却显示 PASS** 的假绿。
>
> ⇒ **P18 MUST 显式以 `json_response=false` 起一个实例来测**（`Task-11` A-02 §6.1 给了完整口径，含「把 `statusWriter.Flush()` 改成空实现，用例 MUST 变红」的负向验证）。`Task-12` A-02 的 L3-5 同样 MUST 按这个口径起 SSE 实例。
>
> 这不意味着要把默认值改成 `false`：默认 `true` 的理由（解析开销小、无流式开销）依然成立，改的是**测试必须自己构造 SSE 形态**。

## 七之二、工具注解（`tools/list` 里的 `annotations`）

MCP 规范的 `ToolAnnotations` 是**客户端决定「要不要弹二次确认」的唯一依据**。不标 = 客户端一律当成危险操作。

🔴 **五个**工具（`ds_search` / `ds_fetch` / `ds_health` / `ds_research` / `ds_extract`）都必须标这三项（`ds_health` 是只读诊断工具，缺 annotation 会让客户端把它当危险操作要求用户确认）：

| 注解 | 值 | 依据 |
|---|:-:|---|
| `readOnlyHint` | `true` | 我们只读上游，不写任何外部状态 |
| `idempotentHint` | `true` | 同参数重复调用结果等价（缓存命中后完全等价；未命中时上游结果有细微差异，但**不产生副作用**，符合规范对幂等的定义） |
| `openWorldHint` | `true` | 结果来自外部开放网络，不是封闭数据集 |

```go
// 注册时 MUST 带上这三项。缺一项都会让客户端把我们当写操作处理。
&mcp.Tool{
    Name: "ds_search",
    Description: ...,
    Annotations: &mcp.ToolAnnotations{
        ReadOnlyHint:   true,       // go-sdk v1.8.0 为 bool
        IdempotentHint: true,       // go-sdk v1.8.0 为 bool
        OpenWorldHint:  boolPtr(true), // 仅此项为 *bool
    },
}
```

`title` 字段另填人类可读名（`"DeepSeek 网页搜索"` / `"DeepSeek 网页抓取"`），客户端 UI 直接显示它。

## 七之三、`/healthz` 探活端点

与 MCP 端点**同端口**，不额外占端口。不受 `path` 影响，路径由 `[server.http] healthz_path` 决定。

| 项 | 规定 |
|---|---|
| 方法 | 只允许 `GET`；其它方法 405 |
| 鉴权 | **不需要** token（探活必须能被 systemd / 监控匿名调用） |
| 返回 | `200` + `application/json` |
| 不查上游 | MUST NOT 发起任何上游请求（否则探活会烧钱） |

响应体（字段顺序固定，便于 diff）：

```json
{
  "status": "ok",
  "name": "DeepSeekSearch",
  "version": "v0.1.0",
  "protocol": "2026-07-28",
  "transport": "streamable-http",
  "uptime_s": 3612,
  "cache": {"entries": 42, "bytes": 1048576, "degraded": false},
  "upstream": {"configured": true}
}
```

🔴 **MUST NOT 出现 `commit` / `build_time` / `go_version` / `upstream.base_url`**（2026-10-25 审计移除）。
本端点按设计排在鉴权中间件**之前**（探活必须免鉴权），所以任何能连上端口的人都能读它；
带上这四项等于送出一份精确的版本指纹 —— 拿到 `go1.27.x` 就能直接对上该补丁版本的已知 CVE，
`base_url` 还顺带说明了流量去向。运维要的完整构建信息在 `ds_health` 的 `build` 段（走 MCP 工具调用）
与 `--version`（走本地 stdout），都不在匿名 HTTP 面上。

| 字段 | 何时为 `degraded`/异常 |
|---|---|
| `cache.degraded` | SQLite 打开失败，已降级为直连。`status` 仍是 `ok` |
| `upstream.configured` | `DEEPSEEK_API_KEY` 为空。此时进程起不来，不会出现 `configured:false` |
| `status` | 恒为 `"ok"`。**只要有响应就是活着**；不可用时连不上，不需要 `status:"degraded"` |

## 七之四、版本号在协议层的三处出口

| 出口 | 位置 | 值来源 |
|---|---|---|
| `serverInfo.version` | `initialize` / `server/discover` 响应 | 编译期注入的 `version` 变量 |
| `/healthz` 的 `version` | 探活响应 | 编译期注入的 `version` 变量。🔴 只有 `version`：`commit` / `build_time` / `go_version` 已从探活响应移除（见 §七之三），它们走 `ds_health` 与 `--version` |
| `--version` 命令行 | stdout 一行 | 同上 |

**MUST NOT** 从 `config.toml` 的 `[app] version` 取值作为协议层版本号 —— 那个字段只是「二进制没注入版本时的兜底显示」。唯一真源是编译期变量。详见 `17-版本与发布契约.md`。

## 八、反向代理要求（部署必须检查）

| 要求 | 违反后果 |
|---|---|
| MUST 透传 `Mcp-Method` | 合法请求被判 400 `-32020` |
| MUST 透传 `Mcp-Name` | `tools/call` 被判 400 |
| MUST 透传 `MCP-Protocol-Version` | 掉进 legacy 路径，拿不到 2026-07-28 能力 |
| MUST NOT 改写头名大小写后丢头 | 部分反代默认丢弃未知头（`Mcp-*` 就是未知头） |
| MUST NOT 缓冲响应 | `X-Accel-Buffering: no`（nginx）；否则 SSE 形态下首包被缓存 |

nginx 片段：

```nginx
location /mcp {
    proxy_pass http://127.0.0.1:8765;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_read_timeout 180s;      # 必须 > fetch total_timeout_ms
    proxy_pass_request_headers on;
}
```

## 九、stdio 传输

| 项 | 规定 |
|---|---|
| 帧格式 | newline-delimited JSON-RPC（SDK 默认） |
| stdout | **MUST 只输出协议帧**，任何日志/调试输出会导致协议解析失败 |
| 🔴 stdout 加固 | 启动时 MUST 按「① 保存原始 fd 1 的 `*os.File` → ② 构造 SDK transport（构造时捕获它）→ ③ `os.Stdout = os.Stderr`」三步执行。理由：禁令与 `TestStdio_NoStdoutPollution` 只能约束**我们自己写的**代码，约束不了依赖库（sqlite 驱动的诊断输出、SDK 升级后新增的 `fmt.Fprintln(os.Stdout, …)`、别处 `init()` 里装错的 slog handler）。`CGO_ENABLED=0`（`17-版本与发布契约.md` §2.2）保证没有 C 代码绕过 Go 的 `os.Stdout` 直接 `write(1, …)`，所以这层兜底在本项目是完备的。完整要求见 `Tasks/Task-11-Transport与架构守护.md` A-01 §3 第 8~10 条 |
| stderr | 日志唯一安全出口（`log.also_stderr = true`） |
| 协议年代 | 从开场交换判定，一次连接钉一个实例 |
| 关闭 | 收到 stdin EOF 或 SIGTERM → 优雅退出 |

## 十一、与 MCPMesh 网关的对接约束

| 项 | 值 |
|---|---|
| 工具全名规则（网关侧） | `<MCP名小写slug>__<工具名>` |
| 我们的工具名 | `ds_search` / `ds_fetch` / `ds_health` / `ds_research` / `ds_extract` |
| 网关上显示 | `deepseeksearch__<工具名>`（五个） |
| 网关需透传的头 | `MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name` |
| 网关是否需要 SSE | 不需要。我们用 `JSONResponse=true` |

**这解决了"要不要实现 SSE 传输"的最后一个悬念**：真有 SSE-only 客户端，交给网关去做协议转换，我们这边保持单档。
