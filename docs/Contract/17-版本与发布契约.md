## 一、版本号规范

### 1.1 格式

```
vMAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]
```

| 段 | 含义 | 本项目规则 |
|---|---|---|
| `MAJOR` | 破坏性变更 | **`0` 期间任何工具名/参数删改都算破坏性**，但 0.x 允许在 MINOR 里做 |
| `MINOR` | 新增功能 | 新增一个 `ds_*` 工具、新增一个配置段 = +1 |
| `PATCH` | 修 bug | 只改行为不改契约 = +1 |
| 前缀 | **统一小写 `v`** | git tag 与显示字符串都用 `v0.1.0`。文档正文里写「V0.1.0」视为同一版本，但**代码与 tag MUST 用小写** |

### 1.2 版本号的三层出现位置（MUST 完全一致）

| 层 | 位置 | 由谁写 |
|---|---|---|
| ① 源码唯一真源 | `Makefile` 的 `VERSION := v0.1.0` | 发版人手工改这一处 |
| ② 编译期注入 | `-ldflags "-X main.version=$(VERSION) ..."` | Makefile 自动 |
| ③ Git tag | `git tag -a v0.1.0 -m "..."` | 发版人手工，MUST 与 ① 相同 |

**MUST NOT** 在 `config.toml` / `README.md` / `CHANGELOG.md` 里有**第二处**「当前版本」的手写数字。README 只指向 `CHANGELOG.md` 顶部。

## 二、注入机制

### 2.1 三个变量（`cmd/deepseeksearch/version.go`）

```go
package main

// 这三个变量只能由链接器注入，代码里的值是「未注入时的开发版标识」。
// MUST NOT 从 config.toml 或环境变量读取 —— 版本号必须描述「这个二进制是什么」，不是「它读到了什么」。
var (
    version   = "v0.0.0-dev"   // -X main.version=v0.1.0
    commit    = "none"         // -X main.commit=a1b2c3d
    buildTime = "unknown"      // -X main.buildTime=2026-10-20T13:05:12Z
)
```

### 2.2 Makefile 注入（原子任务 Task-01 落地）

```makefile
# 版本号唯一真源。发版只改这一行。
VERSION    := v0.1.0
COMMIT     := $(shell git rev-parse --short HEAD 2>/dev/null || echo none)
BUILD_TIME := $(shell date -u +%Y-%m-%dT%H:%M:%SZ)

MODULE  := github.com/LseKit/DeepSeekSearch
LDFLAGS := -s -w \
           -X main.version=$(VERSION) \
           -X main.commit=$(COMMIT) \
           -X main.buildTime=$(BUILD_TIME)

.PHONY: build
build:
	CGO_ENABLED=0 go build -trimpath -ldflags '$(LDFLAGS)' \
		-o ../Bin/DeepSeekSearch ./cmd/deepseeksearch
```

| 参数 | 为什么必须有 |
|---|---|
| `-trimpath` | 去掉构建机绝对路径，保证**可复现构建**：同样的源码在两台机器编出同样的二进制 |
| `-s -w` | 去符号表与调试信息，体积从 12.5MB 降到 ~9MB |
| `CGO_ENABLED=0` | 纯静态二进制。SQLite 用纯 Go 驱动就是要这个效果 |

### 2.3 构建产物命名

```
Bin/DeepSeekSearch                                  # 本地构建，无后缀
Bin/DeepSeekSearch_v0.1.0_linux_amd64               # 发布产物
Bin/DeepSeekSearch_v0.1.0_linux_arm64
Bin/DeepSeekSearch_v0.1.0_darwin_arm64
Bin/DeepSeekSearch_v0.1.0_windows_amd64.exe
Bin/SHA256SUMS                                      # 全部产物的校验和
```

## 三、三处展示出口（MUST 全部实现，MUST 同源）

### 3.1 `--version` 命令行

```
$ DeepSeekSearch --version
DeepSeekSearch v0.1.0 (commit a1b2c3d, built 2026-10-20T13:05:12Z, go1.27.1)
```

| 规则 | 说明 |
|---|---|
| 输出到 **stdout**（不是 stderr） | 脚本要能 `$(DeepSeekSearch --version \| awk '{print $2}')` |
| 单行 | 多行会破坏脚本解析 |
| **不读配置文件** | `--version` 必须在任何 IO 之前返回。目录不存在、配置损坏、Key 缺失都必须是 0 退出 |
| 退出码 `0` | |
| 🔴 go 版本段**只作信息** | 它随**构建工具链**变化（不同机器补丁号可能不同），MUST NOT 对它做精确断言；测试只看 `strings.Contains(out, ", go1.")`。发布产物 MUST 由 CI **构建一次**，MUST NOT 在每台部署机各自构建 |

### 3.2 `serverInfo.version`（MCP 协议层）

`initialize` 与 `server/discover` 响应里的 `serverInfo`：

```json
{
  "serverInfo": {
    "name": "DeepSeekSearch",
    "version": "v0.1.0"
  }
}
```

**MUST 用同一个 `domain.BuildInfo.Version`**，MUST NOT 各算一遍。

### 3.3 `/healthz` 探活响应

```json
{
  "status": "ok",
  "name": "DeepSeekSearch",
  "version": "v0.1.0",
  "commit": "a1b2c3d",
  "build_time": "2026-10-20T13:05:12Z",

  "cache": {"entries": 42, "bytes": 1048576, "degraded": false},
  "upstream": {"configured": true, "base_url": "https://api.deepseek.com"}

```

### 3.4 启动日志首行

```
app.start   version=v0.1.0 commit=a1b2c3d build=2026-10-20T13:05:12Z go=go1.27.1 pid=12345
```

**为什么日志里要打 commit**：用户报 bug 时第一句就是「我用的是最新版」。`commit` 能区分「最新 tag」和「最新 tag + 3 个未打 tag 的提交」。

## 四、`config.toml` 里的 `[app] version` 干什么

| 项 | 规定 |
|---|---|
| 作用 | **仅**日志/`ds_health` 里的兜底显示值。当二进制未注入版本（`v0.0.0-dev`）时，这里能覆盖成人工指定值 |
| 优先级 | 注入值 ≠ `v0.0.0-dev` 时，**注入值胜出**，本项被忽略 |
| 协议层 | 🔴 **MUST NOT** 用于 `serverInfo.version` / `/healthz` / `--version` |
| 为什么保留 | 开发机上 `go run` 不注入版本，此时能看到「这是哪个分支的构建」 |

判定逻辑（Task-02 实现）：

```go
// EffectiveVersion 返回实际对外展示的版本号。
// 注入值有效时忽略配置里的兜底值，保证协议层版本号永远描述二进制本身。
func EffectiveVersion(injected, fallback string) string {
    if injected != "" && injected != "v0.0.0-dev" {
        return injected
    }
    if fallback != "" {
        return fallback
    }
    return "v0.0.0-dev"
}
```

## 五、Git tag 与分支规则

| 项 | 规则 |
|---|---|
| tag 格式 | 附注 tag（`-a`），MUST NOT 轻量 tag。附注 tag 带打 tag 人与日期 |
| tag 名 | `v0.1.0`（小写 v，无前缀） |
| 分支 | `main` 常驻可发布；功能分支 `feat/<slug>`；修复 `fix/<slug>` |
| 发布提交 | MUST 在 `main` 上，且 `git status` 干净 |
| 首个版本 | **`v0.1.0`** —— 不打 `v1.0.0`，因为契约还会随阶段二演进 |

```bash
git tag -a v0.1.0 -m "DeepSeekSearch v0.1.0: ds_search + ds_fetch over stdio and stateless Streamable HTTP"
git push origin v0.1.0
```

## 六、CHANGELOG 规则

位置：仓库根 `CHANGELOG.md`。格式遵循 [Keep a Changelog](https://keepachangelog.com/) 的**结构**，条目用中文。

```markdown
# 变更日志

本项目遵循语义化版本。版本号规则见 `docs/Contract/17-版本与发布契约.md`。

## [未发布]

## [v0.1.0] - 2026-10-20

### 新增
- `ds_search`：DeepSeek 网页搜索，支持 site/lang/after/before/精确短语等结构化语法
- `ds_fetch`：网页正文抓取，支持按标题分节读取，防上下文爆炸
- `ds_health`：本地诊断工具，检查 Key/上游连通/缓存/生效配置
- `ds_research`：搜索 + 并发抓取前 N 条来源，返回带编号引用的单份材料
- `ds_extract`：1~10 个 URL 批量抓取，单条失败只影响该条
- 传输：`stdio` 与无状态 `Streamable HTTP`（MCP 2026-07-28）
- 缓存：SQLite 持久化 + 跨进程 singleflight，防止并发重复计费
- MCP Resource：`ds://error-codes`、`ds://effective-config`、`ds://usage`

### 已知限制
- 不支持 PDF/XML/SVG/ZIP（上游返回 404）
- 无法区分 403/404/500（上游统一塌缩为 404）
- 不做结果重排序（上游已按 rerank_score 降序）
```

| 规则 | 说明 |
|---|---|
| 「未发布」段常驻 | 每次提交往这里加一条，发版时改成版本号 + 日期 |
| 分类固定四类 | `新增` / `变更` / `修复` / `移除` |
| 必写「已知限制」 | 用户最需要知道的是**我们做不到什么** |
| MUST NOT 写 commit hash | 那是 `git log` 的职责 |

## 七、发布检查单（`Scripts/Release.sh` 逐条执行，共 21 项）

> 🔴 **本表项数是唯一真源**。`Release.sh` 的验收 MUST 写成动态判据「项数 = 本表数据行数」，MUST NOT 在别处硬编码数字 —— 此前 `90-Qoder执行手册`（16 项）、`91-验收总表`（17 项）、`18-仓库文件契约`（16 项）、`99-文档验证报告`（16/17 并存）与本表标题（17 项，实际 18 行）给出了**五种**说法，全部源于硬编码。

> 🔴 **变量语法铁律**：本表的命令列全部是 **bash**，版本变量 MUST 写 `${VERSION}`。
> **MUST NOT 写 `$(VERSION)`** —— 在 bash 里 `$(...)` 是**命令替换**，`$(VERSION)` 意思是「执行名为 `VERSION` 的命令」，该命令不存在 ⇒ 展开为**空串** ⇒ `grep -F ""` 匹配一切 ⇒ 版本一致性检查**永远通过**。
> 而版本不一致恰是本项目自己认定的「发版第一号事故源」（见 `90-Qoder执行手册`），三项检查假绿等于没有检查。
> `Release.sh` MUST 在开头取值：`VERSION=$(grep -oP 'VERSION\s*:=\s*\K\S+' Makefile)`，并 MUST 有一条自检：`grep -n '\$(VERSION)' Scripts/Release.sh` 零命中。
