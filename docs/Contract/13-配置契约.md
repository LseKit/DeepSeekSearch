## 一、配置文件分层与优先级

```
环境变量  >  Config/.env  >  Config/config.toml  >  程序内置默认值
```

| 文件 | 放什么 | 权限 | 硬规则 |
|---|---|---|---|
| `Config/config.toml` | 全部**非敏感**配置 | 644 | MUST NOT 出现任何密钥**值** |
| `Config/.env` | **只有** `DEEPSEEK_API_KEY`, 可选 `DEEPSEEKSEARCH_HTTP_TOKEN` | **600** | 权限不对，程序拒绝启动 |
| `Data/` `Logs/` | 运行时产物 | — | 都在项目目录内，不外写 |

> 🔴 **这两个文件是怎么被找到的**（此前只在 `Ops/30-部署运维手册.md` 里隐含，属 F4）：`-config` 默认 `Config/config.toml`、`-env` 默认 `Config/.env`，**两个相对路径都按进程当前工作目录解析**（不是按可执行文件所在目录）。所以 30 号手册里的命令一律先 `cd /mcp/DeepSeekSearch` 再执行，且**不带** `-env` —— 默认值就会被自动发现。flag 的完整默认值表见 `Tasks/Task-12-Cmd装配与发布.md` §3 第 4.1 条。
> `-env` 指向的文件不存在时 **MUST 拒绝启动（3040）**，不能静默跳过：`.env` 是 API Key 的唯一来源，静默跳过只会把错误推迟到第一次上游调用、变成一个难排查的 2401。

### 1.1 启动时会强制检查的 12 件事

| # | 检查 | 不通过时 |
|:-:|---|---|
| 1 | `config.toml` 有没有**密钥类键名**或**密钥形态的值**（判定规则见下方 §1.1.1） | **拒绝启动**（3090，`Detail` 指明违规键名或「值形态疑似密钥」），打印违规行号 |
| 2 | `.env` 权限是否满足 `perm & 0o077 == 0`（group/other 无任何权限） | **拒绝启动**（3090，`Detail` 写明实际权限）。🔴 不是「必须等于 600」—— `0400` 更安全，MUST 放行（Ansible / K8s Secret 挂载默认 0400/0440）。Linux/macOS 生效，Windows 跳过 |
| 3 | `DEEPSEEK_API_KEY` 有没有值 | **拒绝启动**，错误码 3040 |
| 4 | `auth_enabled=true` 时 `DEEPSEEKSEARCH_HTTP_TOKEN` 有没有值且长度 ≥16 | **拒绝启动**，错误码 3041 |
| 5 | 枚举值在不在允许集合里 | **拒绝启动**，错误消息带字段路径 |
| 6 | 数值在不在合法区间（逐项清单见 §1.1.2） | **拒绝启动**，错误消息带字段路径 + 合法区间 |
| 7 | **跨字段约束**是否成立（清单见 §1.1.3） | **拒绝启动**，错误消息同时给出冲突的两个键 |
| 8 | `config.toml` 有没有**未知键**（拼错的） | **拒绝启动**（3090，`Detail` 写明「未知键 `<键名>`」），打印行号 |
| 10 | 配置里有没有 `[hedge]` 段，**或 `server.http.session_timeout_s` 键** | **拒绝启动**（按未知键处理）。二者都是「设了却永不生效」：`[hedge]` 阶段一无实现任务（DEBT-007）；`session_timeout_s` 则因 `ADR-003` 决定「只做无状态、配置里不出现任何 mode/stateless 字段」而**没有任何生效路径**（DEBT-008） |
| 11 | `transport = "stdio"` 时，日志目的地是否包含 stdout | **拒绝启动**（3090，`Detail` 写明冲突项）。stdio 下 stdout 是 MCP 协议通道，一行日志就断会话 |
| 12 | `Asia/Shanghai` 时区能否加载 | 见下方注 —— 已通过 `import _ "time/tzdata"` 消解，正常情况下**不可能失败** |

> **第 8 条最重要**：DeepSeek 上游会**静默忽略**未知字段（实测，见 `23-上游能力实测报告` §3.1），我们绝不能在自己的配置上重犯同一个错。你写错一个参数名，程序不会装作没看见，而是直接告诉你第几行写错了。

> **第 12 条的说明**：`cmd` 包 `import _ "time/tzdata"` 把 IANA 时区库编进二进制（+约 450KB），此后 `time.LoadLocation("Asia/Shanghai")` **不再依赖系统 tzdata**，精简容器与 Windows 均可用。保留这一条只是防御性兜底（例如构建时误用了 `-tags timetzdata_exclude`）。原设计要求的「启动即 `LoadLocation`、失败提示装 tzdata」已无必要，`豁免台账` 中 `domain/time.go` 的 G6 panic 例外亦随之关闭。

#### 1.1.1 密钥检测规则（🔴 改动前 MUST 读完，本条曾打死自家默认模板）

**曾经用过的错误规则**：子串正则 `(?i)(key|token|secret|password|credential)`。

它有一个致命缺陷 —— 本文件 §二 的官方模板自带：

```toml
[server.http]
auth_token_env = "DEEPSEEKSEARCH_HTTP_TOKEN"
```

键名 `auth_token_env` 含 `token` 子串 ⇒ 子串匹配下，**逐字复制 `config.example.toml` 的用户 100% 无法启动**。安全防线打死 happy path，而且是在「照文档做」的路径上，属于最难排查的一类 bug。

**正确规则（两道防线，MUST 都实现）**：

| 防线 | 规则 | 说明 |
|:-:|---|---|
| ① 精确键名黑名单 | 键名（大小写不敏感、取 `[section]` 前缀之后的**最后一段**）**完整等于**下列之一才算违规：`api_key` `apikey` `api_secret` `token` `secret` `password` `passwd` `credential` `credentials` `private_key` | 是**全等**而非子串。`auth_token_env`、`token_header_name` 这类「描述用途」的键名不违规 |
| ② 值形态检测 | 任何键的值匹配 `sk-[A-Za-z0-9]{16,}`，**或** 长度 ≥32 且 Shannon 熵 ≥4.0 → 违规 | 抓住「键名无害但值是密钥」（如 `note = "sk-..."`），防线 ① 覆盖不到 |

**验收 MUST 含三条测试**（缺一条不算完成）：① 默认 `config.example.toml` 逐字加载通过全部 12 项检查；② `[upstream] api_key = "sk-xxxx"` 被拒且 error 含行号与键名；③ `[app] note = "sk-abcdefghijklmnopqrst"` 被拒且 error 指明是「值」违规。

#### 1.1.2 数值区间校验清单（第 6 条的展开，MUST 穷举）

以本项目「未知键即拒启」的严格度，数值校验也 MUST 穷举。原表只列了 7 项，实现时必然遗漏。

| 键 | 合法区间 |
|---|---|
| `server.http.port` | 1 ~ 65535 |
| `server.http.max_request_body_bytes` | ≥1（🔴 原有 `session_timeout_s` 已整键移除，见 §1.1 第 10 条与 DEBT-008） |
| `server.http.max_concurrent_requests` | ≥0（`0` = 不限；超过上限的请求立即返回 429 `3094`） |
| `upstream.max_response_bytes` | ≥1024 |
| `ratelimit.max_inflight` | 🔴 ≥**3**（不是 ≥1）。理由见 §1.1.3 第 8 条：per-key 配额的下限是 search 1 + fetch 2，`max_inflight < 3` 会让「配额之和 > 声明的总额度」自相矛盾 |
| `ratelimit.search_share` | 0 < x < 1（**开区间**：0 会让 search 只能靠 `max(1,·)` 兜底、1 会让 fetch 只能靠 `max(2,·)` 兜底，两种情况都说明这个键被写错了） |
| `ratelimit.max_wait_ms` | 1~300000（🔴 **0 不允许**，与 §3.3、§七 一致；原表写「≥0」是漂移），且见 §1.1.3 跨字段约束 |
| `ratelimit.search.rps`、`ratelimit.fetch.rps` | >0 |
| `ratelimit.search.burst`、`ratelimit.fetch.burst` | ≥1 |
| `ratelimit.warn.window_s` | ≥1；`warn_at_calls` 每项 ≥1 且升序 |
| `timeout.dial_ms`、`tls_handshake_ms`、`response_header_ms` | ≥1，且见 §1.1.3 |
| `timeout.search.per_attempt_ms`、`timeout.fetch.per_attempt_ms` | ≥1 |
| `timeout.search.max_attempts`、`timeout.fetch.max_attempts` | 1 ~ 6 |
| `timeout.search.total_timeout_ms` | ≥1 且 ≤115000 |
| `timeout.fetch.total_timeout_ms` | ≥1 且 ≤115000 |
| `retry.fixed_ms[]`、`retry.spread_ms[]` | 每项 ≥0；两数组长度 MUST 相等 |
| `circuit.fail_threshold`、`half_open_probes` | ≥1；`circuit.open_ms` ≥1 |
| `limits.max_total_chars`、`summary_chars`、`min_content_chars`、`inline_max_chars`、`fixed_chunk_chars` | ≥0（`min_content_chars` ≥1） |
| `limits.budget.*` | ≥0（`0` = 不限） |
| `cache.ttl_fetch_s`、`ttl_search_s`、`wait_ms`、`prune_interval_s` | ≥0（`ttl_*=0` = 不缓存） |
| `cache.max_bytes_mb`、`max_entries`、`max_entry_kb` | ≥1 |
| `dedupe.max_per_domain` | ≥0（`0` = 不限制，见 `Task-02`；**负数 MUST 拒绝**，不能与 0 混用） |
| `log.max_size_mb`、`daily_max_mb`、`max_backups` | ≥1；`log.max_age_days` ≥1；`log.slow_ms` ≥0；`log.max_body_log_kb` ≥0 |

#### 1.1.3 跨字段约束（第 7 条的展开）

| # | 约束 | 违反时 |
|:-:|---|---|
| 1 | `host = "0.0.0.0"` 或 `allow_non_local_host = true` 且 `auth_enabled = false` | **warning 3092** `LOC_HTTP_EXPOSED_NO_AUTH`，不阻断启动（ADR-018）。`auth_enabled` 是唯一鉴权开关；默认值仍是最严的 `host="127.0.0.1"` |
| 2 | `per_attempt_ms × max_attempts + Σ(fixed_ms + spread_ms) ≤ total_timeout_ms`（search 与 fetch **各自**校验；原文只写了 fetch） | 拒绝启动 |
| 3 | `max_wait_ms < min(timeout.search.total_timeout_ms, timeout.fetch.total_timeout_ms)` | 拒绝启动。原区间允许 `max_wait_ms=300000` 而 `total_timeout_ms ≤115000` ⇒ 「合法但必然无效」：排队 5 分钟的语义永远达不到，请求总在 total 处被掐死（3020）。这违背本项目「写错必须当场报错」的哲学 |
| 4 | `per_attempt_ms ≥ dial_ms + tls_handshake_ms + response_header_ms` | **warning**（不是 error）：分层超时会先于 per-attempt 生效，配置虽不矛盾但 `per_attempt_ms` 形同虚设 |
| 5 | `len(retry.fixed_ms) ≥ max_attempts - 1`（search 与 fetch 各自校验） | 拒绝启动。否则 `Delay(attempt)` 越界行为未定义（见 `Task-06`） |
| 6 | `cache.wait_ms` 与 `timeout.fetch.per_attempt_ms` 的关系 | **warning**：跨进程 singleflight 等待者若 `wait_ms` 远小于一次 fetch 时长，几乎必然拿到 3075。默认值下（`wait_ms=8000` vs fetch 最长约 97s）就是这种情形，属有意取舍，但 MUST 在 warning 里给出调参指引 |
| 7 | `total_timeout_ms ≤ 115000` | **warning**：超过常见 MCP 客户端的 120s 工具调用超时，客户端会先掐断，我方拿到的错误变成「客户端超时」，排查困难 |
| 8 | 🔴 `max_inflight ≥ inflight.search + inflight.fetch`，其中两个配额由 `search_share` 推导，且各有下限（search 1、fetch 2） | 拒绝启动，**3090**。推导见 `Task-06` §A-01 3.2：`inflight.search = max(1, floor(max_inflight × search_share))`、`inflight.fetch = max(2, max_inflight - inflight.search)`。当 `max_inflight < 3` 时两个下限会把配额之和顶到 3，超过声明的总额度 ⇒ 配置自相矛盾，MUST 当场报错而不是静默取整 |

> `Validate()` 的签名 MUST 能同时返回 error 与 warning：`Validate() (warnings []string, err error)`。原设计只有 `Validate() error` + `errors.Join`，**warning 没有返回通道**，导致上表第 4/6/7 条无法实现。warning 由 `cmd` 在启动日志里逐条打印，`-check` 模式下同样输出。

## 二、完整配置模板（可直接复制，每行都有中文注解）

```toml
# =============================================================================
#                          DeepSeekSearch 配置文件
#
#  · 本文件只放「非敏感」配置。API Key 请放同目录的 .env（权限 600）。
#  · 所有参数都有内置默认值，写不写都能跑；写了的会覆盖默认值。
#  · 写错的参数名会导致启动失败（不会静默忽略），这是故意的。
#  · 改动的优先级：环境变量 > .env > 本文件 > 内置默认值。
# =============================================================================

# -----------------------------------------------------------------------------
# [app] 程序自身标识
# -----------------------------------------------------------------------------
[app]
# 程序名。出现在 MCP 的 serverInfo 里，日志里也会带。
# 一般不用改，除非你想在同一台机器上跑两份并区分日志。
name = "DeepSeekSearch"

# 版本号兜底显示值。⚠️ 不是协议层版本号的来源。
# 协议层 serverInfo.version / /healthz / --version 全部来自编译期 -ldflags 注入，
# 见 17-版本与发布契约.md。这里只影响日志里那行 "app.start" 的显示。
# 你不需要手改这个值；发版时改 Makefile 的 VERSION 变量。
version = "v0.1.0"


# -----------------------------------------------------------------------------
# [server] 传输方式（怎么和客户端说话）
# -----------------------------------------------------------------------------
[server]
# 传输方式。只有两个合法值：
#   "stdio"            —— 本地进程直连。客户端（Hermes / Qoder / Claude Desktop / Cursor / Codex）
#              会启动本程序，通过标准输入输出通信。适合本机使用。
#   "streamable-http"  —— Streamable HTTP（MCP 2026-07-28 无状态）。
#                         程序监听一个端口，客户端用 URL 连。适合多客户端共享、
#                         或通过 MCPMesh 网关统一接入。
# 选错会怎样：填别的值程序拒绝启动（错误码 3090）。
transport = "streamable-http"

[server.http]
# 只在 transport = "streamable-http" 时生效。

# 监听地址。
#   "127.0.0.1" —— 只有本机能连。默认，最安全。
#   "0.0.0.0"   —— 局域网内其他机器也能连。⚠️ 危险开关，改了等于把工具暴露到网络。
host = "127.0.0.1"

# 监听端口。1~65535。被占用时程序启动失败。默认 8765。
port = 8765

# 端点路径。客户端连接的 URL 就是 http://host:port + 这个路径。
# 例如默认配置下是 http://127.0.0.1:8765/mcp
# 必须以 "/" 开头，不能含空格。一般不用改。
path = "/mcp"

# 响应格式。
#   true  —— application/json。一次请求一次回包，纯 JSON，解析开销小。推荐。
#   false —— text/event-stream（SSE 流）。只有极老的客户端才需要。
# 实际区别：我们不用流式推送，所以 true 更省事也更快。
json_response = true

# 单个请求体的最大字节数。超过返回 413 错误。
# 我们的请求体很小（几百字节），1048576（1MB）已经非常宽松。
max_request_body_bytes = 1048576

# HTTP 入口的并发上限（保护进程与余额）。
#   64（默认）—— 同时在处理的请求上限；超出的请求立即返回 429（3094），不排队。
#   0          —— 不限。⚠️ 无鉴权部署下这等于把并发交给调用方决定。
# 为什么在入口限：`ratelimit` 拦的是「发往上游的调用」，请求体解析、鉴权、
# 排队等入口成本它管不到；无鉴权暴露时，一个客户端就能把 goroutine 堆满。
max_concurrent_requests = 64

# 🔴 原有的 session_timeout_s = 300（「空闲会话超时」）**已整键移除**，理由与
#    [hedge] 完全同型：ADR-003 决定 Streamable HTTP **只做无状态、且配置里不出现
#    任何 mode/stateless 字段**，所以这个键**永不生效**。原注释「无状态模式下基本
#    用不到，留着是为了兼容有状态模式」正是最坏的一种谎言 —— 用户改了它，程序
#    既不报错也不生效。按 §1.1 第 10 条，配置里再写它会**拒绝启动**。
#    有状态模式已于 2026-10-21 裁决不做（见 16 号 DEBT-008）。

# DNS 重绑定防护。
#   false（默认）—— 开启防护：请求来自本机地址但 Host 头不是本机时拒绝。
#   true          —— 关掉防护。⚠️ 危险，除非你明确知道自己在做什么。
disable_localhost_protection = false

# 跨源（Origin）防护。
#   true（默认）—— 校验 Origin 头，防止恶意网页通过浏览器调用你的本地工具。
#   false         —— 关掉。⚠️ 危险开关。
# 为什么必须自己加：实测底层 SDK 默认**不校验** Origin，
# 带 Origin: https://evil.example.com 的请求照样返回 200。
enable_cross_origin_protection = true

# 允许的 Origin 白名单，只在上面为 true 时生效。
#   []（默认，空数组）—— 只允许同源请求。
#   ["https://foo.com"] —— 额外允许这些来源。
# 什么情况需要填：你在浏览器里有个自建面板要直接调这个 MCP，才需要把面板地址加进来。
allowed_origins = []

# 允许非本机 Host 头。
#   false（默认）—— 只接受 Host 是回环地址的请求，其它一律 403。
#   true          —— 放行任意 Host。⚠️ 两种场景该开：前面挂了 nginx/Caddy 等
#                    反向代理且转发原始 Host；或 host = "0.0.0.0" 直连局域网
#                    （客户端的 Host 头是本机 IP，不开这个一律 403/3093）。
# 为什么需要这个开关：hostGuard 只看 Host 头，不看监听地址。
# 与 auth_enabled 相互独立：本项只决定「接不接受这个 Host」，鉴权单独由 auth_enabled 控制。
allow_non_local_host = false

# 健康检查端点路径。客户端不需要它，是给 systemd / nginx / 监控用的。
#   "/healthz"（默认）—— GET 返回 200 + JSON
#   ""                —— 关闭该端点（不推荐）
# 与 MCP 端点同端口，不额外占端口。
healthz_path = "/healthz"

# HTTP 传输的 Bearer 鉴权。
#   false（默认）—— 不鉴权。
#   true          —— 要求请求头带 Authorization: Bearer <token>。
#                   token 从 .env 的 DEEPSEEKSEARCH_HTTP_TOKEN 读取（不放本文件）。
# 本项是**唯一**的鉴权开关（ADR-018）：暴露到网络时也能为 false，但启动期会打
# 3092 警告 —— 不鉴权就等于任何能连上的人都能花你的钱。
auth_enabled = false

# 鉴权 token 的环境变量名。一般不改。
# 值不写在这里，写在 .env 里；本文件只写「从哪个变量读」。
auth_token_env = "DEEPSEEKSEARCH_HTTP_TOKEN"


# -----------------------------------------------------------------------------
# [upstream] 上游 DeepSeek API 连接参数
# -----------------------------------------------------------------------------
[upstream]
# 上游地址。
#   "https://api.deepseek.com" —— 官方，默认。

# -----------------------------------------------------------------------------
# [ratelimit] 限流（防止把上游打崩）
# -----------------------------------------------------------------------------
[ratelimit]
# 同时"在路上"的请求数上限。超出的排队等待，不拒绝。
# 为什么要有：客户端可能一次性并发调用 50 个工具，不设上限会把本机打满。
# 🔴 这是**总额度**，两个工具各自分到一份配额，不共享（见下方 search_share）。
max_inflight = 8

# search 在 max_inflight 里占的比例。剩下的全部给 fetch。
#   inflight.search = max(1, floor(max_inflight × search_share))
#   inflight.fetch  = max(2, max_inflight - inflight.search)   ← 下限 2，MUST NOT 为 0
# 为什么要有这个键：令牌桶已经按工具隔离了，但在飞数若是**全局**一个信号量，
# search（实测 0.3s 级、rps=30）瞬时就能占满 8 个名额，fetch（45s 级）只能排队到
# max_wait_ms 超时 —— 这正是本项目最想避免的"搜索把抓取饿死"，只是从令牌桶挪到了信号量。
# 调小的后果：search 并发受限更早排队。调大的后果：fetch 配额被挤压（但受下限 2 保护）。
# 裁决与推导见 Tasks/Task-06-Resilience限流重试预算熔断.md §A-01 3.2。
search_share = 0.5

# 排队最长等多久（毫秒）。超时才返回错误（3000 LOC_QUEUE_TIMEOUT）。
# 这是唯一保留的"硬边界" —— 不能去掉，否则卡住的请求会永久占着 goroutine 不释放。
# 调大的后果：请求更容易成功，但客户端可能先超时。
# 🔴 令牌与在飞名额**两段共用这一个** deadline，所以最坏总等待 ≤ max_wait_ms（不是 2×）。
#    3000 的 details.stage = "token" | "inflight"，用于分辨是速率不够还是并发不够
#    （二者调的旋钮不同：rps vs max_inflight）。见 Task-06 §A-01 3.3。
max_wait_ms = 30000

[ratelimit.search]
# 搜索接口的令牌桶速率（每秒允许多少个请求）。
# 🔴 默认由 60.0 改为 30.0，依据 23 号 §6.2 的实测：
#    search 端点 40 并发 → **40×200，零 429**；fetch 端点 60 并发 → 32×200 + 28×429。
#    ⇒ 两端点**分别限速**，且 search 侧未探到硬上限。
#    原值 60 的立论是「实测跑到 26 QPS 没触发 429，取 60 留余量」—— 那是**突发**通过，
#    不等于**持续**速率安全；60 缺任何余量证据，撞 429 后只会靠退避重试烧时间。
#    30 = 已验证突发（40）之下、且给 fetch 留足上游总额度。
# 调小的后果：请求排队变多、整体变慢。调大的后果：更容易撞上游 429。
rps = 30.0
# 桶容量。允许的瞬时突发量。设成 rps 的 2 倍，与实测通过的 40 并发同量级。
burst = 60

[ratelimit.fetch]
# 抓取接口的令牌桶速率。与搜索**互相独立**（23 号 §6.2 实测确认上游对两者分别限速）。
# 🔴 硬上限实测为 **25 QPS**：429 的 message 原文是
#    `Too many requests. Please pace your requests reasonably. Your current QPS: 25`
#    （`16-技术债登记表` X3 原记 26，已按实测改为 25）。取 20 留 20% 余量。
rps = 20.0
burst = 40

[ratelimit.warn]
# 软告警：只记日志 + 在响应里加 warnings，**不阻断**。
# 统计窗口（秒）
window_s = 60
# 窗口内调用次数达到这些值时各记一次 WARN 日志。想关掉就写 []
warn_at_calls = [100, 500, 1000]


# -----------------------------------------------------------------------------
# [timeout] 分层超时（这才是对付"网络慢"的正确办法）
# -----------------------------------------------------------------------------
[timeout]
# 这三个是底层 HTTP 参数，对所有请求生效。
# TCP 建连超时（毫秒）
dial_ms = 5000
# TLS 握手超时（毫秒）
tls_handshake_ms = 5000
# 等响应头超时（毫秒）。服务器开始回数据的最大等待时间。
response_header_ms = 30000

[timeout.search]
# 单次尝试的总时长上限（毫秒）。
# 实测搜索很快：0.27~0.71 秒。12 秒足够宽松。
per_attempt_ms = 12000
# 最多尝试几次（含第一次）。
# 4 次 = 最多 3 次重试。搜索便宜又快，多试几次很划算。
max_attempts = 4
# 整个调用（含排队 + 所有重试）的总时长上限（毫秒）。
# 🔴 67000 = 4×12000（per_attempt × max_attempts）+ 19000（Σ fixed+spread）
#          = 48000 + (1000+3000+8000) + (1000+2000+4000)。
#    原值 60000 **小于最坏情况** ⇒ 第 4 次尝试必被总闸门掐断，等于「配了 4 次却只跑 3 次」。
#    改 max_attempts 或 per_attempt 时，MUST 按 §1.1.3 第 2 条的公式重算本值。
total_timeout_ms = 67000

[timeout.fetch]
# 单次尝试的总时长上限（毫秒）。
# 🔴 必须 > 31000：实测上游网关超时是 30 秒（go.dev 那个页面 30.1 秒才返 504）。
# 设小了会在上游还在干活时把自己掐断。
per_attempt_ms = 45000
# 最多尝试几次（含第一次）。
# 🔴 为什么是 2 不是 3：Hermes 的 MCP 工具调用超时默认 120 秒。
# 3 次 × 45s = 135s 会被客户端先掐断，我们拿到的错误会变成"客户端超时"，排查困难。
# 2 次最坏 45+45+7 = 97 秒，留 23 秒余量。
max_attempts = 2
# 整个调用的总时长上限（毫秒）。必须 < 客户端超时（Hermes 是 120000）。
total_timeout_ms = 110000
# ⚠️ 如果你用 Qoder 且它报超时，把 per_attempt_ms 改成 25000，max_attempts 保持 2（最坏 57 秒）


# -----------------------------------------------------------------------------
# [retry] 重试（防抖动、防网络瞬断）
# -----------------------------------------------------------------------------
[retry]
# 总开关。false = 失败就直接返回，不重试。
enabled = true

# 退避模式：
#   "fixed_plus_random"（默认）—— 固定基数 + 随机增量：
#                                  每个等待 = fixed_ms[i] + rand(0, spread_ms[i])
#   "full"                      —— 完全随机：rand(0, fixed_ms[i] × 2^attempt)
#   "none"                      —— 固定等待：就等 fixed_ms[i]，不加随机
# 为什么默认 fixed_plus_random：固定值保证"网络抖一下不会立刻又打"，
# 随机增量保证"多个进程不会同一毫秒一起打"。比纯随机更好解释、更好在日志里核对。
jitter_mode = "fixed_plus_random"

# 每次重试前的固定等待基数（毫秒）。数组长度 = max_attempts - 1。
# 默认 [1000, 3000, 8000] 意思是：第1次重试等1秒，第2次等3秒，第3次等8秒。
# 为什么不设更短：网络抖动的重传窗口常在 1~3 秒，2 秒内重试基本等于白重试。
fixed_ms = [1000, 3000, 8000]

# 每次重试的随机增量上限（毫秒）。实际等待 = fixed_ms[i] + rand(0, spread_ms[i])。
# 默认 [1000, 2000, 4000] → 实际等待区间 1.0~2.0s / 3.0~5.0s / 8.0~12.0s
spread_ms = [1000, 2000, 4000]

# 🔴 原键 `respect_retry_after` **已删除**，替换为下面这个。
#    为什么：23 号 §6.3 实测 60 并发触发的**全部 28 个 429 响应**里，
#    `Retry-After` / `x-ratelimit-*` / `ratelimit-*` 头**零出现**。
#    也就是说 `respect_retry_after` 是一个**永不生效的孤儿配置** ——
#    用户把它设成 true 会以为「上游会告诉我等多久」，实际永远走固定退避表。
#    这正是本项目反复批评上游的那条罪状（给了参数但不生效），我方 MUST NOT 自己犯。
#
# 替代方案：429 的 message 里带了真实 QPS 数值（`Your current QPS: 25`）。
# 开启后，`resilience` 会正则提取该数值并据此**自适应降速**（把对应桶的 rps
# 临时压到提取值以下，维持 `adapt_cooldown_s` 秒后按 1.5 倍逐步回升，不超过配置值）。
# 提取失败（上游改了文案）则静默退回固定退避表，不报错。
parse_qps_from_429 = true
# 自适应降速的维持时长（秒）。到期后开始回升。
adapt_cooldown_s = 60

# 什么情况下重试。可选项：
#   "429" 上游限流 / "408" 上游读体超时 / "502" "503" "504" 上游网关类错误
#   "net_error" 网络层错误（连接重置、DNS 失败、TLS 失败）
#   "timeout" 我们自己的超时
# 显式不重试（写进来也无效）：400 401 402 403 404 413
#   理由：这几种重试 100% 得到同样结果，纯烧钱。402 是余额不足，等你充值才行。
retry_on = ["429", "408", "502", "503", "504", "net_error", "timeout"]

[retry.budget]
# 重试预算。这是防止"重试风暴"的关键 —— 也是"激进重试"能安全存在的前提。
# 开启后统计最近 window_s 秒内的 重试次数 / (总请求数 + 重试次数)。
# 一旦超过 ratio，新的重试直接拒绝（返回 3010），避免上游一慢所有客户端一起放大流量。
enabled = true
# 上限比例。0.10 = 最多把上游流量放大 1.11 倍。
# 调大的后果：更容易把上游打崩。调小的后果：重试基本用不上。
ratio = 0.10
# 统计窗口（秒）
window_s = 60

[circuit]
# 熔断器。和重试互补：重试管"这一次能不能救回来"，熔断管"整条链路是不是已经死了"。
enabled = true
# 连续失败几次就打开熔断。打开后所有请求立即失败（不发上游），持续 open_ms。
fail_threshold = 5
# 熔断打开时长（毫秒）。过了这段时间进入半开状态试探。
open_ms = 15000
# 半开状态放几个试探请求。成功就恢复正常，失败就重新打开。
half_open_probes = 2

# -----------------------------------------------------------------------------
# [limits] 返回内容的预算与粒度
# -----------------------------------------------------------------------------
[limits]
# 单次工具调用返回的字符总上限（按 rune 计，一个中文字 = 1）。
# 超过就按相关性得分从高到低截断，并在响应里标 truncated=true + truncated_by="budget"。
# 实测参考：count=10 + detail=summary 约 12,900 字符。
# 🔴 但这个默认值**在 count=50 时一定会触发截断**：50 × summary_chars(1200) = 60,000 rune
#    > 32,000，也就是约一半的结果会被丢掉。这是**设计上的取舍**（上下文预算优先于结果完整性），
#    MUST 在 `ds_search` 的 description 里写明：「count 较大时靠后的结果可能被预算截断，
#    响应里的 `total` 是过滤前条数、`results` 是实际返回条数，两者不等即说明发生了截断」。
# 调小的后果：更容易丢靠后的结果。调大的后果：上下文占用变多。
max_total_chars = 32000

# 搜索默认返回几条（1~50）。用户不填 count 时用这个值。
# 实测参考：10 条约 10k token。
default_count = 10

# 搜索结果默认详细程度。可选四档：
#   "minimal" —— 只给标题/URL/日期/权威度/得分。约 60 token/条。适合先看列表再决定。
#   "snippet" —— 加 100~200 字的命中片段。约 180 token/条。适合判断"要不要抓这一页"。
#   "summary"（默认）—— 加片段 + 600~1200 字的定向摘要。约 1000 token/条。
#                        实测这个摘要是"跟着你的问题变的"，所以能直接用来回答，不必再抓页面。
#   "content" —— 加网页正文全文。token 不定，可能几万。只在确实需要原文时用。
default_detail = "summary"

# 单条 summary 的字符上限。
# 🔴 实测上限由 1535 修正为 **2008**（23 号 §3.3，50 条样本区间 518~2008；
#    官方文档声称 600~800，明显偏低）。1200 的默认值仍保留 —— 它是**我方主动的**
#    token 预算，不是「上游最长多少就设多少」。
# 调到 0 = 不截断（不推荐：单条 2008 rune × 50 条 = 100K rune，必然撞 max_total_chars）。
summary_chars = 1200

# 抓取页面时，正文短于这个字符数就认为"抓到的是导航栏不是正文"，返回 3050 错误。
# 实测有的页面只返回 121 字（全是导航）。120 是个安全阈值。
min_content_chars = 120

# 抓取时如果正文 ≤ 这个字符数，直接返回全文；超过则返回"目录"，让模型按章节取。
# 为什么要有这个阈值：短页面返目录等于让模型多调一次，浪费往返。
# 校准建议：一般页面正文 2000~6000 字，8000 能覆盖大多数；长文档（RFC/书籍）才会走目录模式。
inline_max_chars = 8000

# 无标题文档（纯文本 / JSON / RSS）按这个长度均分切片。
fixed_chunk_chars = 8000

# 🔴 ds_fetch 的 outline（目录）模式最多返回多少节。超出只返回前 N 节，
#    并在 warnings[] 里写明「目录已折叠，共 M 节」。
# 为什么必须有这一项：outline 是**唯一此前完全没有预算约束**的返回形态 ——
# `max_chars` 原本只管内联正文，`max_total_chars` 只管 ds_search。
# 实测 pkg.go.dev/net/http 有 139,685 rune，标题极密的文档可产生数百上千节，
# 每节含 id/level/title/chars + 200 rune 预览 ⇒ **光一份目录就能到 100K+ 字符**，
# 等于用一个「目录」绕过了本项目反复强调要防的「568K 字符塞爆上下文」。
# 200 节足够任何正常文档使用；真需要更多说明该文档不适合用 outline 模式读。
outline_max_sections = 200

# [cache] 缓存（省钱的核心）
# -----------------------------------------------------------------------------
[cache]
# 总开关。关掉 = 每次调用都真实请求上游，每次都计费。
enabled = true

# 缓存后端。阶段一只有 "sqlite" 一个合法值。
# 为什么用 SQLite 而不是内存：stdio 模式下每个客户端各起一个进程，

db_path = "Data/Cache.db"

# 抓取结果的缓存时长（秒）。默认 21600 = 6 小时。
# 实测依据：同一页面 6 小时内不会变；而 Search 返回的 URL 大量带 utm_* 参数，
# 上游缓存会被 utm 击穿，所以只有我方按"规范化 URL"缓存才真正省钱。
# 调小的后果：省得少。调大的后果：可能拿到过期页面。
ttl_fetch_s = 21600

# 搜索结果的缓存时长（秒）。
# 🔴 默认由 0 改为 **180**（3 分钟）。原立论已被实测推翻，见 ADR-014 与 23 号 §3.4：
#    原文写「同一 query 连发 4 次，字节数 12437/12437/12204/12490 ⇒ 上游结果非确定性」。
#    2026-10-20 复测：同一 query 连打 3 次，**16,962 字节、sha256 三次全等** ——
#    短窗口内 search 是**字节级稳定**的。原来那 4 次的长度差异更可能来自
#    跨了索引更新窗口，而不是「每次都不一样」。
# 🔴 「模型无从察觉是快照」这个顾虑不成立：命中缓存时响应里 MUST 带
#    `from_cache=true` + `cached_at` + `age_seconds`（见 `12-数据契约` §十 本地扩展字段），
#    调用方**能**察觉。
# 取 180 的权衡：够长以省钱（同一个 agent 在几分钟内反复搜同一 query 很常见），
# 又够短以不让索引新鲜度成为问题。需要严格实时就设 0（不缓存，每次都计费）。
ttl_search_s = 180

# 最多存多少条。超了按"最久没被访问"淘汰。
max_entries = 500

# 缓存总占用上限（MB）。超了同样按 LRU 淘汰。
max_bytes_mb = 256

# 单条缓存的体积上限（KB）。超过就不写缓存（**静默**不写，只记一条 warn）。
# 🔴 默认由 1024 改为 **2048**，依据 23 号 §4.3/§4.4 的实测：
#    · 原文写「实测单次响应最大 636KB」—— 复测发现 **RFC 9110 正文就有 439,285 字节**，
#      而 HTML spec 281,905 rune、pkg.go.dev/net/http 139,685 rune，大页面并不罕见；
#    · 更关键的是**中文页 byte ≈ rune × 2.2~2.4**（实测 CSDN 首页 1,913 rune / 4,505 byte，
#      百度首页 456/1,010）。一个 500K rune 的中文长页 ≈ **1.5MB**，在 1024KB 上限下
#      会被**静默丢弃**。
# 🔴 「静默不写缓存」的连带危害比省下的磁盘严重得多：跨进程 singleflight 的 owner
#    成功拿到了内容但永不写值，于是所有等待者要么空等到 `cache.wait_ms` 超时（3075），
#    要么抢占租约**再打一次上游** —— 恰好是这套设计要消灭的重复计费。
#    详见 `Task-07` 的租约时序修正（Put 成功后才 DELETE 租约）。
# 调到 4096 也安全：`max_bytes_mb = 256` 与 `max_entries = 500` 才是真正的总量闸门。
max_entry_kb = 2048

# 跨进程等待时长（毫秒）。
# 场景：两个客户端同时抓同一个 URL。先到的去打上游，后到的等它写进缓存，最多等这么久。
# 避免"两个进程同时打上游 = 双倍计费"。
wait_ms = 8000

# 过期条目清理周期（秒）。每这么久扫一遍删掉过期数据。
prune_interval_s = 300

# 缓存打不开时是否允许降级继续跑。
#   true（默认）—— 记 ERROR 日志 + warn.cache_degraded，然后无缓存直连。工具仍可用，只是每次都计费。
#   false         —— 直接拒绝启动。
# 为什么默认允许降级：缓存是「省钱」不是「功能」，缓存挂了不该让整个 MCP 变砖。
degraded_ok = true
```

### 3.3 `[ratelimit]`

| 参数 | 类型 | 默认 | 可选值 | 选了会怎样 |
|---|---|---|---|---|
| `max_inflight` | int | `8` | 🔴 3~64（原写 1~64，但 per-key 配额下限是 search 1 + fetch 2，`<3` 自相矛盾，见 §1.1.3 第 8 条） | 太小排队多；太大本机连接数吃紧 |
| `search_share` | float | `0.5` | 0 < x < 1 | 🔴 **新增键**。search 在 `max_inflight` 里占的比例，余量全给 fetch。默认 0.5 ⇒ 8 拆成 search 4 / fetch 4。在飞数不隔离就会重演「搜索把抓取饿死」（`Task-06` §A-01 3.2） |
| `max_wait_ms` | int | `30000` | 1~300000 | **0 不允许**（立即失败）。这是唯一不能去掉的硬边界。🔴 令牌与在飞名额两段**共用**这一个 deadline ⇒ 最坏总等待 ≤ `max_wait_ms`（不是 2×），见 `Task-06` §A-01 3.3 |

## 六、默认值的设计依据（每条都不是拍的）

| 默认值 | 依据 |
|---|---|
| `search.rps = 30` | 🔴 **由 60 下调**（23 号 §6.2）：search 40 并发 → **40×200 零 429**，未探到硬上限；原立论「实测跑出 26 QPS」是**突发**通过、不代表持续速率安全，60 缺任何余量证据。30 在已验证突发（40）之下，且给 fetch 留足上游总额度。官方文档写 5，你的情报是 100 —— 二者都与实测不符 |
| `fetch.rps = 20` | 🔴 硬上限**实测确认 25 QPS**：429 的 message 原文 `Too many requests... Your current QPS: 25`（`16-技术债登记表` X3 原记 26，已改）。取 20 留 20% 余量 |
| `search_share = 0.5` | 🔴 **新增键**。令牌桶按工具隔离了，但在飞数若是全局一个信号量，search（实测 0.3s 级、`rps=30`）瞬时就能占满 8 个名额，fetch（45s 级）只能排队到 `max_wait_ms` 超时 —— 把「搜索饿死抓取」从令牌桶挪到了信号量。0.5 是**无偏起点**（两个工具各拿一半），fetch 侧另有下限 2 保护，因为单次 fetch 最长 45s、配额为 1 时一个慢站就能让第二个请求排满 30s 后失败。推导见 `Task-06` §A-01 3.2 |
| `max_inflight = 8` | 本机并发上限。🔴 合法区间由 1~64 收紧为 **3~64**：per-key 配额下限是 search 1 + fetch 2，`<3` 会让配额之和超过声明的总额度（§1.1.3 第 8 条） |
| `fetch.per_attempt_ms = 45000` | 实测 `go.dev/doc/go1.27` 30.1s 才返 504；设 30s 会自己掐断仍在执行的请求。🔴 23 号 §4.6 精确值：并发冷抓取 go.dev/doc/effective_go 时，2 个失败请求的 504 **精确出现在 30.126s / 30.131s** ⇒ 上游网关 30s 硬超时，45000 = 30s + 50% 余量 |
| `fetch.max_attempts = 2` | Hermes 的 MCP 工具调用超时默认 120s；3 次 × 45s = 135s 会被客户端先掐断 |
| `retry.fixed_ms = [1000,3000,8000]` | 网络抖动重传窗口常在 1~3s；2 秒内重试等于白重试 |
| `retry.budget.ratio = 0.10` | 重试放大上限 1.11 倍，与 Google SRE 的 retry budget 一致 |
| `circuit.fail_threshold = 5` | 单次故障不足以判定上游死亡，5 次连续失败是稳定信号 |
| ~~`hedge.enabled = false`~~ | 🔴 **`[hedge]` 整段已从阶段一模板移除**（DEBT-007）：14 个 Task 里没有任何实现任务，而本项目对未知键零容忍。留着会造成最坏的一种谎言 —— 用户设 `true`，程序不报错也不生效。现在写 `[hedge]` 段会**拒绝启动**（§1.1 第 10 条）。该项已于 2026-10-21 裁决不做（见 16 号 DEBT-007） |
| `limits.default_count = 10` | 实测 10 条 ≈ 10k token，是你确认的取值 |
| `limits.default_detail = "summary"` | 实测 summary 是 **query 定向摘要**（同一 URL 在不同 query 下 105~967 字），可直接支撑回答 |
| `limits.summary_chars = 1200` | 🔴 实测单条最长 **2008** 字（50 样本区间 518~2008，23 号 §3.3；原文记的 1535 已修正）；不设上限会被长文拉爆 |
| `limits.max_total_chars = 32000` | 实测 `count=10 + summary` ≈ 12,900 字符，32000 基本不触发截断。🔴 **但 `count=50` 时必然触发**：50 × 1200 = 60,000 rune > 32,000，约一半结果会被丢掉。这是**有意的取舍**（上下文预算优先于结果完整性），故 `ds_search` 的 description MUST 写明「`total` 是过滤前条数、`results` 是实际返回条数，两者不等即说明发生了截断」 |
| `limits.outline_max_sections = 200` | 🔴 **新增**。outline 此前是唯一无预算约束的返回形态：pkg.go.dev/net/http 实测 139,685 rune，标题极密文档可产生上千节，每节含 200 rune 预览 ⇒ 光目录就能到 100K+ 字符 |
| `cache.ttl_search_s = 180` | 🔴 **原立论已被推翻**（ADR-014）。原文「4 次 12437/12437/12204/12490 ⇒ 非确定性」；23 号 §3.4 复测同 query 连打 3 次 **16,962 字节、sha256 三次全等**，短窗口内字节级稳定。且「失真不可被察觉」也不成立 —— 命中缓存时响应带 `from_cache`/`cached_at`/`age_seconds`。180s 兼顾省钱与索引新鲜度 |
| `cache.ttl_fetch_s = 21600` | 网页正文 6 小时内基本不变；实测上游对 utm 击穿缓存，我方缓存是唯一有效层 |
| `cache.max_entry_kb = 2048` | 🔴 实测 RFC 9110 正文 **439,285 字节**、HTML spec 281,905 rune（23 号 §4.3；原文记的「最大 636KB」已不适用）；且中文页 **byte ≈ rune×2.2~2.4**，500K rune 长页 ≈1.5MB。1024 会**静默丢缓存**并连带击穿 singleflight。总量由 `max_bytes_mb`/`max_entries` 把关 |
| `dedupe.max_per_domain = 3` | 实测 `site:github.com/golang/go` 50 条全同域，会污染结果集 |
| `search.min_rerank = null` | 实测固定阈值 2.0 在不同 query 上保留率 0%~100%，会整批变空 |
| `search.min_authority = null` | 实测同 query 内 authority 几乎全同值，过滤无效 |
| 危险开关缺省最严 | 宪章 §八：改变安全姿态的开关，默认值必须是最严格的那一档 |

## 七、危险开关清单（改动 MUST 留审计）

| 开关 | 默认 | 改动后的风险 |
|---|---|---|
| `server.http.host` | `127.0.0.1` | 改 `0.0.0.0` = 暴露到网络；若同时 `auth_enabled=false` 则启动打 3092 警告（裸奔，ADR-018） |
| `server.http.allow_non_local_host` | `false` | 放行任意 Host（含 DNS rebinding 路径）；必须与 `auth_enabled = true` 同时开 |
| `server.http.disable_localhost_protection` | `false` | 关掉 DNS rebinding 防护（SDK 只在「本连接来自回环地址且 Host 非回环」时拒 403；反代到回环监听时靠它放行） |
| `server.http.enable_cross_origin_protection` | `true` | 关掉 = 任意网页可调本地工具 |
| `upstream.base_url` | 官方 | 改自建代理 = 失去上游 SSRF 保护 |
| `retry.budget.enabled` | `true` | 关掉 = 重试可无限放大 |
| `retry.parse_qps_from_429` | `true` | 关掉 = 撞 429 后只按固定退避表等，不再自适应降速 |
| `search.min_rerank` / `min_authority` | `null` | 填值 = 某些 query 可能返回 0 条 |

## 八、本文件与实现的一致性保证

| 保证 | 机制 |
|---|---|
| 配置结构体字段与本文件一一对应 | `internal/config/config.go` 每个 struct 的注释指向本文件对应小节 |
