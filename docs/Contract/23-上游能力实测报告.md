## 二、端点与探活

| 请求 | 实测结果 | 含义 |
|---|---|---|
| `POST /v1/tools/search` | 200 / 400 / 401 / 429 | 正式端点 |
| `POST /v1/tools/fetch` | 200 / 400 / 404 / 429 / 504 | 正式端点 |
| `GET /` | **404，空 body** | 不能用于探活：无法区分「网络通但 base_url 错」与「路径错」 |
| `GET /v1/tools/search` | **405，空 body** | ✅ **推荐探活方式**：走真实路由，405 ≠ 200 故不计费 |
| `HEAD /v1/tools/search` | **405** | 同上，但部分代理会改写 HEAD |
| `POST /v1/tools/nonexistent` | **404** | ⇒ base_url 或路径配错时得到 404，**与 fetch 的 404 语义完全不同** |
| `GET /v1/models` | **200 + 模型列表** | 免费，但依赖 Key 有 chat 权限；受限 Key 会误报不可达 |

**决策**：见 `ADR-015`（Ping 用 `GET {base}/v1/tools/search` 期望 405）。

诊断价值：Ping 得到 **404 而非 405** ⇒ `upstream.base_url` 配错；得到 **401** ⇒ Key 失效；得到 **405** ⇒ 链路健康。

## 三、Search 接口实测

### 3.1 请求参数边界（全部为 HTTP 400 + `type=invalid_request_error`）

| 请求体 | 上游 message（去掉 request_id） | 结论 |
|---|---|---|
| `{"query":"x","ori_question":""}` | `'ori_question' must be between 1 and 128 characters` | **空串必须置 nil**，复现原结论 |
| `{"query":"x","ori_question":null}` | 200 | `null` 等同未提供 |
| `{"query":"x","count":null}` | `Invalid JSON request: invalid type: null, expected u32 at line 1 column 33` | **count 必须省略而非传 null**，复现原结论 |
| `{"query":"x","count":0}` / `51` | `'count' must be between 1 and 50` | 边界严格 |
| `{"query":"x","count":-1}` | `invalid value: integer \`-1\`, expected u32` | 上游是 **Rust/serde** 后端 |
| `{"query":""}` / `{"query":"   "}` | `'query' must not be empty` | **全空白等同空** |
| `{"count":1}`（缺 query） | `missing field \`query\`` | — |
| `{"query":123}` | `invalid type: integer \`123\`, expected a string` | — |
| `{"query":"x","totally_unknown_field":"x","foo":{"a":1}}` | **200** | **未知字段静默忽略**（复现原结论，也是本项目对自家配置零容忍的理由） |
| `{"query":"x","localization":""}` | **200** | 空串被接受 |
| `{"query":"x","localization":"not-an-ip"}` | `'localization' must be a valid IP address` | ⇒ **我方 MUST 先校验**，见 §3.1.1 |
| `{"query":"x","need_content":"yes"}` | `invalid type: string "yes", expected a boolean` | — |
| `{}` | `missing field \`query\`` | — |

#### 3.1.1 query 长度口径 = **rune（Unicode 标量），不是 byte**

| 输入 | rune 数 | byte 数 | 结果 |
|---|---|---|---|
| 127 个汉字 | 127 | 381 | **200** |
| 128 个汉字 | 128 | 384 | **200** |
| 129 个汉字 | 129 | 387 | **400** `'query' must be at most 128 characters` |
| 128 个 ASCII | 128 | 128 | **200** |
| 129 个 ASCII | 129 | 129 | **400** |
| 129 个 `🚀`（U+1F680） | 129 | 516 | **400** |

⇒ `domain.SliceByRune` 与「按 rune 计」的铁律**实测成立**。emoji 按 1 rune 计（非 UTF-16 的 2），说明上游按 Unicode 标量计数。

> **推论**：`BuildQuery` 拼装后的 128 rune 检查是正确的，但错误码要用 **1010 `VAL_QUERY_TOO_LONG`**，不是 1090（见 14 号契约）。

### 3.2 搜索语法操作符

对照实验：基词 `DeepSeek`，`count=5`，逐一加操作符比对结果域名与日期。

| 操作符 | 是否生效 | 实测证据 |
|---|:-:|---|
| `site:` | ✅ | `site:github.com` → 5 条全为 github.com |
| `site:a OR site:b` | ✅ | → github.com + huggingface.co 混合 |
| `-site:` | ✅ | `-site:deepseek.com` → 基线第 1 位 `api-docs.deepseek.com` 消失 |
| `lang:` | ✅ | `lang:en` → 结果集与基线明显不同（出现 huggingface.co、blog.csdn.net） |
| `after:` / `before:` | ✅ | `before:2026` → 返回 2025-12-14 / 2025-08-20 / 2025-05-27 |
| `"精确短语"` | ✅ | 结果集变化 |
| `-"排除短语"` / `-排除词` | ✅ | 结果集变化 |
| **非法值** | ❌ **静默忽略** | `after:abc` → **HTTP 200**，无任何报错 |

#### 3.2.1 🔴 `after:YYYY` 年份语义陷阱（高价值发现）

| query | 返回结果的 date |
|---|---|
| `DeepSeek`（基线） | 2026-10-16 / 2026-10-17（北京时间） |
| `DeepSeek after:2025` | **全部 2026-10-16** |
| `DeepSeek after:2025-01-01` | 全部 2026-10-16 |
| `DeepSeek after:2026-01-01` | 全部 2026-10-16 |
| `DeepSeek after:2026-10-01` | 全部 2026-10-16 |
| **`DeepSeek after:2026`** | **0 条** ← 尽管基线结果的日期正是 2026-10 |
| `DeepSeek before:2026` | 2025-12-14 / 2025-08-20 / 2025-05-27 |
| `DeepSeek before:2027` | 全部 2026-10-16 |

⇒ **`after:YYYY` 的语义是「晚于该年」= `>= (YYYY+1)-01-01`，不是「该年起」**；`before:YYYY` 是「早于该年」= `< YYYY-01-01`。

**风险**：LLM 被要求「找 2025 年之后的资料」时几乎必然写 `after:2025`，结果**静默丢掉整个 2025 年**，且不报任何错。这正是本项目定义的最危险错误类型（静默错误结果）。

**处置**：`BuildQuery` MUST 把裸年份 `after:YYYY` 展开为 `after:YYYY-01-01`（`before:YYYY` 保持原语义，因为「早于 2026 年」= `< 2026-01-01` 与直觉一致）；同时 ds_search 的 `after` 参数 description MUST 写明该规则。

#### 3.2.2 上游零语法校验 ⇒ 参数注入会静默改变查询意图

`after:abc` 返回 200 证明上游**不解析、不校验**操作符值，只做透传。因此：
- `exact_phrase` 含 `"` 会破坏 `"..."` 配对，改变整个查询语法；
- `site` 含空格会引入意外的 `OR`/操作符；
- `exclude_terms` 含 `site:` 会变成站点过滤。

⇒ ds_search MUST 对 `exact_phrase` / `exclude_terms` / `site` / `exclude_sites` / `ori_question` / `localization` 做输入校验，**不能依赖上游报错**。

### 3.3 响应字段实测分布

样本：`人工智能 大模型 技术`，`count=50`，`need_content=false`。

| 字段 | 实测 | 官方文档声称 | 差异处置 |
|---|---|---|---|
| `date` 时间部分 | **40/40 恒为 `16:00:00+00:00`** | 示例写 `2026-06-01T00:00:00+00:00` | ⇒ **官方示例误导**。`2026-10-16T16:00:00Z` 转 Asia/Shanghai = `2026-10-17T00:00:00+08:00`，故 `domain.ParseDate` 的「先 `In(Asia/Shanghai)` 再取日期」规则**实测成立且必需**，否则日期差一天 |
| `date` 为 `null` | **10/50 = 20%** | 「未知时为 null」 | ⇒ null 是**常态**（1/5），`age_days` 必须可空，排序与过滤必须处理 null |
| `authority` | 仅 **1 / 2 / 3 / 4**（另一批 100 条冷门样本亦同） | 「0~4，**-1 表示未知**」 | ⇒ 未观测到 0 与 -1，但官方声明其存在。`min_authority` 过滤时 **`authority < 0` MUST 视为未知、不参与过滤**，否则 `min_authority=0` 会静默丢弃未知权威度的结果 |
| `rerank_score` | 1.807 ~ 2.380（热门）；**0.196 ~ 1.505（冷门）** | 「0~3，**>=1.5 为优质**」 | ⇒ 见 §3.3.1 |
| `snippet` | **81 ~ 269** 字符 | 「通常 100~200」 | 超出官方区间，MUST NOT 假设上界 |
| `summary` | **518 ~ 2008** 字符 | 「通常 600~800」 | ⇒ **上限 2008，比 13 号记录的 1535 高 31%**。`limits.summary_chars=1200` 的截断会真实触发 |
| `content` | `need_content=false` 时恒为 `""` | 同 | 复现 |
| `site_name` | **null 9/50 = 18%** | 「缺失时为 null」 | ⇒ 输出层必须处理 null，minimal 档含该字段 |
| `site_icon` | null 0/50 | 「缺失时为 null」 | 形如 `https://cdn.deepseek.com/site-icons/<域名>` |
| `url` scheme | **http 明文 10/50 = 20%** | 未说明 | ⇒ `NormalizeUrl` 与去重 MUST 明确 `http://x` 与 `https://x` 是否同一 key |

#### 3.3.1 🔴 `min_rerank=1.5` 在长尾 query 上会返回 0 条

5 个冷门 query × `count=20` = 100 条样本：

| query | rerank 区间 | **< 1.5 占比** | authority 分布 |
|---|---|---|---|
| 个人博客 随笔 记录 | 1.274 ~ 1.505 | **95%** | 1×14, 2×5, 3×1 |
| small personal blog notes | 1.086 ~ 1.335 | **100%** | 1×10, 3×7, 4×3 |
| 论坛 帖子 求助 | 0.970 ~ 1.173 | **100%** | 1×3, 2×15, 3×2 |
| site:blogspot.com travel diary | 1.188 ~ 1.415 | **100%** | 1×19, 2×1 |
| 未知小站 测试页面 | 0.196 ~ 0.594 | **100%** | 1×7, 2×5, 3×6, 4×2 |

⇒ 官方文档的「≥1.5 为优质结果」在长尾场景下会**过滤掉全部结果**。ds_search 的 `min_rerank` description MUST 明确警告：「1.5 是热门 query 的优质线；冷门/专业/小语种 query 的正常结果普遍低于 1.5，设置该值可能返回 0 条。**不确定时不要传**」。`min_authority` 同理（authority=1 在冷门 query 占 19/20）。

### 3.4 结果确定性 ⇒ 推翻 `ttl_search_s = 0` 的立论

同一 query `DeepSeek V3 架构`（`count=5`）**连续 3 次**调用：

| 次序 | 响应 bytes | sha256(前12) | URL 列表 |
|---|---|---|---|
| 1 | 16,962 | `7033165dacd8` | m.gmw.cn, api-docs.deepseek.co, jas.ia.ac.cn, www1.scnet.cn, mlcommons.org |
| 2 | 16,962 | `7033165dacd8` | 同上 |
| 3 | 16,962 | `7033165dacd8` | 同上 |

⇒ **字节级完全相同**。13 号契约 `cache.ttl_search_s = 0` 的立论（「实测 4 次 12437/12437/12204/12490」）在**短窗口内不成立**；观测到的差异应来自跨小时/跨天的索引更新。

**决策**：见 `ADR-014`（`ttl_search_s` 由 0 改为 180）。

### 4.1 请求参数边界

| 输入 | 结果 | message |
|---|---|---|
| `file:///etc/passwd` | **400** | `'url' must be an HTTP or HTTPS URL with a host` |
| `ftp://example.com/x` | **400** | 同上 |
| `http://user:pass@example.com/` | **400** | `'url' must not contain credentials` |
| `""`（空串） | **400** | `'url' must be a valid HTTP or HTTPS URL` |

⇒ **上游已自行校验 scheme / credentials / 长度 / host**。我方 ds_fetch 的本地校验是**纵深防御 + 省下必然失败的一次往返**，不是唯一防线。

### 4.2 SSRF：上游侧行为

| 目标 | 结果 |
|---|---|
| `http://127.0.0.1/` | **404** `failed to fetch URL` |
| `http://localhost/` | **404** 同 |
| `http://10.0.0.1/` | **404** 同 |
| `http://169.254.169.254/latest/meta-data/` | **404** 同 |
| `http://2130706433/`（十进制混淆 IP） | **404** 同 |

⇒ 上游拦截了内网目标，**但响应与真 404 完全不可区分**。因此：
1. 我方**不能**通过响应判断上游是否拦截成功；
2. 本地黑名单仍有价值（避免把本服务当作探测放大器、覆盖 `base_url` 指向自建代理的情形）；
3. **威胁模型表述必须修正**：抓取由上游执行，我方进程从不直连目标 URL，黑名单保护的不是「我方出网」。

**原表 `[/#.,:{}()\-!]`（11 个）→ 实测全集 32 个，缺 21 个。原表中的 11 个全部被观测到（无多余项）。**

#### 4.5.1 🔴 存在嵌套转义 ⇒ MUST 单趟替换

观测到 26 处 `\\`，上下文如：

```
\#\# 1\\\. Introduction
\#\# 2\\\. Model Summar
```

原文本身已含 `\.`（源 Markdown 里的转义），上游再转义一层 ⇒ `\\\.`。

- **单趟** `ReplaceAllString(`\\(.)`, "$1")`：`\\\.` → `\.`（正确，只脱一层）
- **多趟**（如按字符逐个 `strings.ReplaceAll` 循环）：`\\\.` → `\.` → `.`（**过度反转义，丢失原文语义**）

⇒ `domain.Unescape` MUST 用**单次正则全量替换**，MUST NOT 用字符循环。

#### 4.5.2 🔴 Search 侧**不转义** ⇒ MUST NOT 对其调用 Unescape

`need_content=true` 的 search 响应（8 条结果）统计：

| 字段 | 转义总数 | 不同字符 |
|---|---|---|
| `content` | **6** | 仅 `\n`（代码块内的字面换行转义） |
| `snippet` | **0** | — |
| `summary` | **0** | — |
| `title` | **0** | — |

⇒ **只有 fetch 的 `content` 被 Markdown 转义**。若对 search 结果调用 `Unescape`，会把代码片段里的 `\n` 变成字母 `n`（若字符集扩到含 `n` 则更糟）。

**结论**：`Unescape` 的调用点 MUST 仅限 ds_fetch 的正文路径；ds_search 的 content/summary/snippet/title **禁止**调用。

### 4.6 🔴 上游 fetch 有 **30 秒硬超时**，且并发冷抓取会触发 504

冷启动测试：`https://go.dev/doc/effective_go`（本次会话从未抓取过），5 个请求**同时**发出：

| 请求 | HTTP | 耗时 | runes | sha256(前12) |
|---|:-:|---|---|---|
| 并发1 | 200 | 4.051s | 105,162 | `77309a6eca99` |
| 并发2 | 200 | 4.126s | 105,162 | `77309a6eca99` |
| 并发4 | 200 | 4.152s | 105,162 | `77309a6eca99` |
| **并发3** | **504** | **30.126s** | — | — |
| **并发5** | **504** | **30.131s** | — | — |

单请求超时复现：`html.spec.whatwg.org/` → 504；`w3.org/TR/html52/single-page.html` → 504。504 的 `type=gateway_timeout_error`、message=`Request timeout`。

⇒ 三条结论：

1. **上游网关硬超时 = 30s**（两个样本 30.126s / 30.131s）。`timeout.fetch.per_attempt_ms = 45000` **正确**（必须 > 30000 才能拿到上游的 504 而不是自己先掐断），`13-配置契约` 的 🔴 注释成立。
2. **成功的并发响应内容字节级完全相同**（3 个 sha256 全等）⇒ **推翻** `Task-07` / `Task-09` 记载的「同一 URL 5 并发返回 5 种长度（168K~429K）」。真实的分歧来源是 **504 超时**，不是内容不确定。间隔 30s 重抓同一 URL 仍字节相同。
3. **singleflight 的必要性依然成立，但理由要换**：并发冷抓取同一 URL 会导致**部分请求 30s 超时失败 + 全部请求各自计费**。⇒ 跨进程 singleflight 是正确的，`Task-07` 的证据段必须改写为上述实测。

### 4.7 正文量级 ⇒ `truncated_by` 启发式会大量误报

| 页面 | runes | 末尾内容 | 是否截断 |
|---|---|---|:-:|
| `rfc-editor.org/rfc/rfc9110.html` | **437,738** | `...48155 Münster\n\nGermany` | **否**（RFC 编辑器地址块，真实结尾） |
| `html.spec.whatwg.org/multipage/parsing.html` | 281,905 | `...Return fragment.` | 否 |
| `pkg.go.dev/net/http` | 139,685 | `...Click to hide internal directories.` | 否 |
| `stackoverflow.com/questions/11227809` | 98,047 | `...See similar questions with these tags.\n\ndefault` | 否 |
| `go.dev/doc/effective_go` | 105,162 | — | 否 |

`Task-09` 的启发式规则是：`total_chars ∈ [100000, 600000]` **且** 末尾不在句号/换行/闭合标签 → 判 `truncated_by="upstream"`。

⇒ **RFC 9110（437,738 rune，末尾 `Germany`）落在窗口内且末尾不匹配 ⇒ 假阳性**。而它是一份完整文档。同类还有 `pkg.go.dev`（末尾是 `.`，恰好躲过）。

**结论**：该启发式的立论（「上游静默截断且并发长度不一致」）已被 §4.6 推翻 —— 上游的真实失败模式是 **504 超时**，不是静默截断。⇒ **删除字符数窗口启发式**；`truncated_by="upstream"` 仅在拿到确定信号时填写，否则不填；504 作为独立的可重试错误（2504）处理。

## 五、错误响应实测

### 5.1 结构与 `type` / `code` 对照表

统一结构（OpenAI 兼容），`param` **恒为 `null`**：

```json
{"error":{"message":"<文本> (request_id: <uuid>)","type":"<t>","param":null,"code":"<c>"}}
```

| HTTP | `type` | `code` | message 样例 |
|---|---|---|---|
| 400 | `invalid_request_error` | `invalid_request_error` | `'count' must be between 1 and 50` |
| 401（缺 Key） | `authentication_error` | `invalid_request_error` | `Authentication Fails (missing key)` |
| 401（错 Key） | `authentication_error` | `invalid_request_error` | `Authentication Fails, Your api key: ****0000 is invalid` |
| 404 | `not_found_error` | **`invalid_request_error`** ← 不一致 | `failed to fetch URL` |
| 429 | `rate_limit_error` | **`invalid_request_error`** ← 不一致 | `Too many requests. Please pace your requests reasonably. Your current QPS: 25` |
| 504 | `gateway_timeout_error` | `gateway_timeout_error` | `Request timeout` |

⇒ 🔴 **`error.code` 不可作为判据**：404 与 429 都返回 `invalid_request_error`，与其语义完全不符。**MUST 按 HTTP status 映射错误码**（即 `Code = 2000 + status`，`Task-05` 现有方案正确）。`type` 字段语义较准，可作为日志附加信息，但 MUST NOT 参与错误码决策（上游可能调整措辞）。

### 5.2 `request_id` 只在 message 文本里

- 错误响应：message 尾部恒有 `(request_id: <uuid>)`，格式为 8-4-4-4-12 的标准 UUID（小写十六进制）。
  ⇒ `Task-05` 的正则 `\(request_id:\s*([0-9a-fA-F-]{8,64})\)` **实测成立**。
- **200 响应没有 request_id**。响应头只有 `x-ds-trace-id: <32位hex>`（如 `7f1a6adb8a7a8306c62ec633dfd96d3e`）。
- 上游声明了 `access-control-expose-headers: x-ds-request-id`，但**该头在实测的所有响应中均未出现**（含 401）。

⇒ **MUST NOT 依赖响应头获取 request_id**；成功调用若要关联上游日志，只能用 `x-ds-trace-id`（建议记入日志的 `upstream_trace_id` 字段，便于报障）。

### 5.3 密钥回显面

401（错 Key）的 message 含 `Your api key: ****0000 is invalid` —— 上游已掩码，仅回显**后 4 位**。

⇒ 该 message 会进入 `UpstreamError.UpstreamMsg` → `ErrorPayload` → 日志与 LLM 可见的错误体。虽然只有后 4 位，仍 MUST 在落日志前对 `upstream_msg` 做二次脱敏（正则 `api key: \*+\w+` → `api key: ****`），避免与其它日志行拼接后泄露更多。

## 六、限流实测

### 6.1 fetch：25 QPS 硬上限

60 个并发 `POST /v1/tools/fetch`（同一 URL `https://go.dev/blog/`）：

| 状态码 | 数量 |
|---|---|
| 200 | **32** |
| **429** | **28** |

429 完整响应体：

```json
{"error":{"message":"Too many requests. Please pace your requests reasonably. Your current QPS: 25 (request_id: f67f23f8-...)","type":"rate_limit_error","param":null,"code":"invalid_request_error"}}
```

⇒ **上游限流阈值 = 25 QPS**，且 message **直接回报当前 QPS**（可用于自适应降速）。`16-技术债登记表` X3 记的「实测 26」应更正为 **25**。

### 6.2 search：40 并发零 429

40 个并发 `POST /v1/tools/search`（`count=1`，query 各异）：**40 × 200，零 429**。
先前 25 并发亦全 200。

⇒ **两个端点分别限速、不互相占用额度**（复现 `13-配置契约` `[ratelimit.fetch]` 的注释结论）。search 的实际阈值 > 40 并发，未探到上限。

### 6.3 🔴 429 **不返回** `Retry-After`，也没有任何 ratelimit 头

对上述 28 个 429 响应与全部 200 响应做响应头扫描：

```
grep -ihoE '^(retry-after|x-ratelimit[a-z-]*|ratelimit[a-z-]*):' → 零命中
```

200 响应的完整头集合（实测）：

```
server: openresty
content-type: application/json
vary: accept-encoding
vary: origin, access-control-request-method, access-control-request-headers
access-control-allow-credentials: true
access-control-expose-headers: x-ds-request-id
x-ds-trace-id: <32hex>
strict-transport-security: max-age=31536000; includeSubDomains; preload
x-content-type-options: nosniff
content-length / date
eo-log-uuid / eo-cache-status: MISS      ← 腾讯 EdgeOne CDN
```

⇒ 🔴 **`[retry].respect_retry_after = true` 是永不生效的孤儿配置**。

**处置**（二选一，见 13 号契约）：
- **(a) 删除该配置项**（推荐）—— 保留会让用户以为它有效；
- **(b) 改为解析 429 message 里的 `Your current QPS: (\d+)`** 做自适应降速（信息量其实**大于** `Retry-After`：它告诉我们超了多少）。若采用，配置项 MUST 改名为 `parse_qps_from_429` 之类，避免误导。

## 八、复现方式

关键结论的最小复现集（约 20 次调用，¥0.1）。执行前 MUST 从 `Config/.env` 读 Key，MUST NOT 把 Key 写进命令行历史或日志。

```bash
set -euo pipefail
: "${DEEPSEEK_API_KEY:?需要 Key}"
B=https://api.deepseek.com
H=(-H "Authorization: Bearer ${DEEPSEEK_API_KEY}" -H 'Content-Type: application/json')

# 1. after:YYYY 年份语义陷阱（§3.2.1）—— 期望 after:2026 返回 0 条
for q in "DeepSeek after:2026" "DeepSeek after:2026-01-01"; do
  printf '%-28s ' "$q"
  curl -sS "${H[@]}" -d "{\"query\":\"$q\",\"count\":3}" "$B/v1/tools/search" \
    | python3 -c 'import json,sys;print(len(json.load(sys.stdin).get("results",[])),"条")'
done

# 2. search 结果确定性（§3.4）—— 期望 3 次 sha256 全等
for i in 1 2 3; do
  curl -sS "${H[@]}" -d '{"query":"DeepSeek V3 架构","count":5}' "$B/v1/tools/search" | sha256sum
done

# 3. fetch 30s 硬超时 + 并发内容一致（§4.6）—— 期望部分 504@~30s，成功者 sha 全等
for i in 1 2 3 4 5; do
  ( curl -sS "${H[@]}" -d '{"url":"https://go.dev/doc/effective_go"}' "$B/v1/tools/fetch" \
      -o "/tmp/f$i.json" -w "  HTTP=%{http_code} t=%{time_total}s\n" ) &
done; wait

# 4. 429 阈值与无 Retry-After（§6）—— 期望部分 429，且 grep 零命中
for i in $(seq 1 60); do
  ( curl -sS -D "/tmp/h$i" "${H[@]}" -d '{"url":"https://go.dev/blog/"}' "$B/v1/tools/fetch" \
      -o /dev/null -w '%{http_code}\n' ) &
done; wait
grep -ihoE '^(retry-after|x-ratelimit[a-z-]*):' /tmp/h* || echo "  无 Retry-After / ratelimit 头"

# 5. 转义字符全集（§4.5）—— 期望 32 种
curl -sS "${H[@]}" -d '{"url":"https://github.com/deepseek-ai/DeepSeek-V3"}' "$B/v1/tools/fetch" \
  | python3 -c 'import json,re,sys;c=json.load(sys.stdin)["content"];print(len(set(re.findall(r"\\\\(.)",c))),"种:",sorted(set(re.findall(r"\\\\(.)",c))))'

# 6. 探活端点（§二）—— 期望 405 / 404 / 200
for p in /v1/tools/search / /v1/models; do
  printf '  GET %-20s ' "$p"; curl -sS -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer ${DEEPSEEK_API_KEY}" "$B$p"
done
```
