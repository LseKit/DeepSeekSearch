# 18 · 仓库文件契约（GitHub 发布标准）

> **文件路径**：`/mcp/DeepSeekSearch/GitHubSrc/docs/Contract/18-仓库文件契约.md`
> **用途**：**推到 GitHub 的每一个文件**的清单、位置、硬规则、验收命令的唯一真源。缺一个不许打 tag。
> **创建日期**：2026-10-20
> **依据**：GitHub 官方 community health files 清单；OpenSSF Scorecard 检查项；Go 官方与 Google/Uber Go Style Guide；AGENTS.md 开放格式（LF Projects）
> **状态**：已冻结（v0.1.0）

## 一、分级定义

| 级别 | 含义 | 缺失后果 |
|:---:|---|---|
| **A 必须** | 没有它就不构成一个「可发布的公开仓库」 | **禁止打 tag** |
| **B 大厂标准** | GitHub / Google / Microsoft 级别项目的默认配置 | CI 会红，或 OpenSSF Scorecard 扣分 |
| **C 条件项** | 满足特定条件才需要 | 条件成立时补 |
| **D 明确不做** | 评估过，本项目不需要 | 已登记理由，见 §六 |

> 🔴 **A2 的 `grep -c 'LseKit/DeepSeekSearch' LICENSE` = 1 与「MUST NOT 改写 MIT 正文」不冲突**（C12 裁决）。
>
> 曾有人指出：标准 MIT 正文不含仓库 URL，而 `Task-13` 又规定 MUST NOT 改写正文一个字 ⇒ 这条验收可能永假。**实际不会永假**：`Tasks/Task-01-项目骨架与构建系统.md` §5.8 的逐字正文里，**版权行**就是
>
> ```text
> Copyright (c) 2026 小逸 <https://github.com/LseKit/DeepSeekSearch>
> ```
>
> URL 在版权行（MIT 模板本来就留了这一行给版权人填），不在 `Permission is hereby granted …` 那几段正文里。所以 `grep` 命中的是版权行，两条规则同时成立。
>
> ⇒ **MUST NOT** 为了「让 grep 过」往 MIT 正文里塞 URL：那会同时破坏 A2 的逐字性要求与 GitHub 的许可自动识别（识别失败 → 徽章不显示、依赖扫描无法判断兼容性）。若哪一天版权行格式要改，MUST 同步改这里、`Task-01` §5.8、`Task-14` 的 `CheckRepoFiles.sh` 三处。

## 四、关键文件的详细规范

### 4.1 `ci.yml` 的 6 个**核心** job（MUST 全部存在，顺序固定）

| # | job | 命令 | 失败含义 |
|:-:|---|---|---|
| 1 | `fmt` | `gofumpt -l . \| tee /dev/stderr \| wc -l` 必须为 0 | 格式没跑 |
| 2 | `lint` | `golangci-lint run ./...` | 静态检查不过 |
| 3 | `size` | `bash Scripts/CheckSize.sh . docs`（🔴 **两参**；文档根是仓库内 `docs`，漏了会加载不到豁免台账） | 撞规模红线 |
| 4 | `test` | `go test -race -count=1 ./...` | 测试红或竞态 |
| 5 | `cover` | 总覆盖率 ≥ 65%；**逐包**：Domain / Config / Resilience ≥ 80%，`internal/tools` ≥ 70%（`Task-08`/`Task-09` 的承诺，没有这一行就没有牙齿） | 覆盖不足 |
| 6 | `drift` | `bash Scripts/CheckDocDrift.sh docs .` + `bash Scripts/CheckRepoFiles.sh .` + 校验 `docs/` 存在且非空 | 文档漂移 / 发布文件缺失 / `docs/` 缺失 |

**顺序要求**：`fmt` → `lint` → `size` → `test` → `cover` → `drift`。便宜的放前面，早上红早省时间。

> 🔴 **为什么 `drift` job 要跑三条而不是一条**：`CheckDocDrift.sh` 只比对**文档↔代码**，它管不到「`AGENTS.md` 与 19 号文档漂移」「A/B 级发布文件被误删」「`docs/` 目录缺失」—— 这三件事原本都要等到发版那一刻（`Release.sh` 第 1 / 18 项）才暴露。两个脚本都是秒级，没有理由不放进 CI。

**另有 3 个 job 不参与上面这条顺序链**（`CheckRepoFiles.sh` 数「6 个 job」时只数上表这 6 个名字，MUST NOT 把它们算进去）：

| job | 作用 | 为什么必须有 |
|---|---|---|
| `cross-build` | `GOOS=linux/darwin/windows` × `GOARCH` 的编译矩阵 | 否则 darwin/windows 产物要到 release 那一刻才**第一次**交叉编译 |
| `vuln` | `govulncheck ./...` | `SECURITY.md` 把「`go.sum` 里某个依赖的已知 CVE」列为**受理**问题，CI 却没有任何漏洞扫描 ⇒ 承诺没有牙齿 |
| `win-smoke` | Windows runner 上跑 `--version` 与 `-check` | 验证 `import _ "time/tzdata"` 真的生效。Windows 没有系统 tzdata，`cmd` 包漏这一行则**启动即 exit 1**（`Contract/10-包依赖矩阵.md` §2.9） |

**MUST 有的三行**：

```yaml
permissions:
  contents: read          # 最小权限。Scorecard 的 Token-Permissions 直接看这个

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true  # 同一分支新提交取消旧跑，省额度
```

**🔴 全链 MUST pin**（Scorecard `Pinned-Dependencies`）：Go 工具（gofumpt / golangci-lint / gocyclo / govulncheck）pin 到**具体版本号**并集中在 workflow 顶部的 `env:`；第三方 action pin 到 **40 位 commit digest**（`@v4` 这种 tag 引用不算 pin）。`@latest` 的三重后果：① Scorecard 大面积扣分，§九 那句「Supply-Chain 都能拿到分」不成立；② `golangci-lint@latest` 将来出 v3 时 v2 的配置格式会直接红 CI（`Task-13` 自己就警告过这类事故）；③ 同一 commit 两次 CI 结果可能不一致。跟进由 `.github/dependabot.yml` 的 `github-actions` ecosystem 负责。

### 4.2 `release.yml` 的产物清单（MUST 全部产出）

| 产物 | 命名 |
|---|---|
| Linux amd64 | `DeepSeekSearch_v0.1.0_linux_amd64` |
| Linux arm64 | `DeepSeekSearch_v0.1.0_linux_arm64` |
| macOS arm64 | `DeepSeekSearch_v0.1.0_darwin_arm64` |
| Windows amd64 | `DeepSeekSearch_v0.1.0_windows_amd64.exe` |
| 校验和 | `SHA256SUMS` |
| SBOM（🔴 **全项目一份**，SPDX JSON） | `DeepSeekSearch_v0.1.0.sbom.json` |

> 🔴 **SBOM MUST 标出依赖 scope**：`go.mod` 里有 5 个 require，其中 `github.com/google/go-cmp` 是**仅测试**依赖、不进二进制（`Contract/10-包依赖矩阵.md` §2.10.1：运行时 4 个 + 仅测试 1 个）。不标 scope 会有两个后果：① README 宣传「只有 4 个第三方依赖」与 SBOM 的 5 行看起来互相打脸；② `govulncheck` 报 go-cmp 的漏洞时无法判断可达性，只能当发版阻塞处理（正确处置是「不可达（test-only）」+ 记进 `16-技术债登记表` 跟踪升级）。
>
> 🔴 **SBOM 只有一份，不是「每平台一份」**（C13 修正）。`anchore/sbom-action` 扫的是**依赖图**（`go.mod` / `go.sum`），而四个平台产物的依赖图**完全相同**（`CGO_ENABLED=0` + 纯 Go SQLite 驱动 ⇒ 没有平台专属依赖）。原文的注释与命名 `_<os>_<arch>.sbom.json` 描述了一个 workflow 里根本没实现的行为 —— 注释与产物不符是「读注释的人以为有四份、去 Release 页只找到一份」的经典来源。真要按平台区分，得改成逐平台 `go list -deps` 后再各生成一份，本项目没有这个需要。

**MUST NOT** 把二进制提交进 git（Scorecard `Binary-Artifacts` 直接判 0）。二进制只出现在 Release 附件里。

**🔴 `workflow_dispatch` 手输 tag 的两道闸门**（否则可以绕过整个 CI 与 `Release.sh` 的 21 项检查发版）：

| # | 闸门 | 不加的后果 |
|:-:|---|---|
| 1 | 发布 job MUST `needs:` 一个**校验 tag 真实存在**的 job（`git rev-parse --verify "refs/tags/${tag}"`） | `softprops/action-gh-release` 对不存在的 tag 会**自动创建 tag + release** ⇒ 在 Actions 页面手输一个 `v9.9.9` 就能凭空发出一个版本 |
| 2 | 发布 job MUST `needs:` CI（用 `workflow_call` 把 `ci.yml` 当可复用工作流调用） | tag 推送不触发 `push: branches` 规则 ⇒ 原本 CI 根本没跑，红代码也能发版 |

### 4.3 `AGENTS.md` 的定位（最容易被写错的一份）

| 问题 | 答案 |
|---|---|
| 它和 README 的区别 | README 给人（快速开始、项目描述）；AGENTS.md 给 **agent**（构建步骤、测试命令、契约、禁止清单） |
| 有强制字段吗 | **没有**。AGENTS.md 就是普通 Markdown，agent 解析你给的文本 |
| 冲突谁赢 | 离被改文件最近的 AGENTS.md 赢；用户在对话里的显式指令覆盖一切 |
| 本项目的用法 | Qoder/Hermes 开新窗口时**第一份必读**。它里面的命令 agent 会真的去跑 |
| 篇幅上限 | 建议 ≤ 500 行。它不是文档库，是「不读就会做错」的东西的集合。详细设计放 `docs/` |

### 4.4 `SECURITY.md` 的必含四要素

| 要素 | 本项目取值 |
|---|---|
| 支持版本 | 只支持最新 tag（v0.1.x）。更早版本不修 |
| 上报方式 | GitHub Security Advisories 私密上报（`/security/advisories/new`）；**MUST NOT** 开公开 issue |
| 响应时限 | 72 小时内确认收到；7 天内给初步评估；修复窗口按严重度（Critical 7d / High 30d / 其他 90d） |
| 范围说明 | **哪些算安全问题**：API Key 泄漏、SSRF 绕过（IP 混淆 / 重定向）、鉴权绕过、`/healthz` 信息泄漏、`go.sum` 已知 CVE；**哪些不算**：上游返回的 404、搜索结果质量、DeepSeek 服务本身、🔴 **DNS 重绑定**（理由见下） |

> 「哪些不算」这一节比「哪些算」更重要 —— 否则一半的 issue 是「我搜不到东西」。

> 🔴 **DNS 重绑定 MUST 写在「哪些不算」里，MUST NOT 写在「哪些算」里**（C12 裁决，`Tasks/Task-13-发布文件与社区治理.md` §5.3 的骨架已按此改）。
>
> | 项 | 内容 |
> |---|---|

### 4.6 🔴 commit type ↔ release notes 分组的映射（谁打 label）

`CONTRIBUTING.md` 规定的提交信息 type 词表（`feat` / `fix` / `docs` / `refactor` / `test` / `build` / `chore`）与 `.github/release.yml` 的分组（按**标签**分组）此前是**两套无映射的词表**，且**没有定义谁打 label** ⇒ `generate_release_notes: true` 产出的分组基本全落在「其他变更」，等于没分类。

**裁决：以 PR 标签为准，标签由 commit type 前缀推导，映射固定如下。**

| commit type | PR label | `release.yml` 分组 | 谁负责 |
|---|---|---|---|
| `feat` | `feat`（或 `enhancement`） | 新增 | 提 PR 的人 MUST 自己打；漏打由 `CODEOWNERS` 指派的 reviewer 补 |
| `fix` | `fix`（或 `bug`） | 修复 | 同上 |
| `docs` | `docs` | 文档 | 同上 |
| `build` / `ci` | `build` / `ci` | 构建与 CI | 同上 |
| `refactor` / `test` / `chore` | 无需 label | 其他变更 | — |
| dependabot PR | `dependencies` | 依赖更新 | dependabot 自动打（`.github/dependabot.yml` 的 `commit-message.prefix` 是 `chore(deps)`，但 label 由 `package-ecosystem: gomod` 自动加 `dependencies`） |
| 任何 type | `skip-changelog` | **不出现** | 维护者手工加 |

**为什么取「按 label 分组 + 从 commit type 推导」而不是「改成按 commit 前缀分组」**：GitHub 的 `release.yml` **只支持按 label 分组**，没有「按 commit message 前缀分组」这个能力（`generate_release_notes` 的分类维度就是 label 与作者）。所以映射只能落在 label 上；能做的是把「谁打 label」写死，避免它变成没人负责的空档。

🔴 squash merge（§七 第 3 条）会把一个 PR 压成一条 commit，其 message 取自 PR 标题 ⇒ **PR 标题 MUST 以 `<type>(<scope>):` 开头**，这样即使漏打 label，`CHANGELOG.md` 的手工条目也能从 `git log` 里正确归类。`PULL_REQUEST_TEMPLATE.md` 的「变更类型」勾选框 MUST 与实际 label 一致。
