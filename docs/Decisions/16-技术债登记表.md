## 四、已知不修的缺陷（明确 `不做`）

| # | 项 | 为什么不做 |
|:-:|---|---|
| N1 | PDF / XML / SVG / ZIP 抓取 | **实测上游全部返回 404**。不是我们不支持，是上游不支持。已在 `14-错误契约` §2.3 的 2404 成因里写明 |
| N2 | 区分 403 / 404 / 500 | **实测上游把三者塌缩成同一个 404**。做不到，不是不做 |
| N3 | 结果重排序 / 加权打分 | **实测 6/6 query 返回时已按 `rerank_score` 单调降序**。对已排序列表再做一次重排 = 用更少的信息去覆盖更多信息 |
| N4 | 固定阈值过滤（`min_rerank`） | **实测同一阈值 2.0 在不同 query 上保留率 0%~100%**（`行政复议法` 全部 1.77~1.89 → 会清空）。默认 `null`，参数留着给调用方自担风险 |
| N5 | 答案合成（`synthesize`） | 调用方本身就是 LLM，拿着用户的完整上下文；我们的合成模型只看得到 `query`，看不见意图。合成还会**销毁引用**并把 prompt injection 藏进正文 |
| N6 | Tavily 形状的兼容 API | 我们不是通用搜索网关。多一套 API 形状 = 多一套契约要维护 |
| N7 | 多用户 / 多租户 / BYOK | 单用户自用工具。多租户是 MCPMesh 网关的职责 |
| N8 | 403/404 时退回匿名 HTTP 抓取 | **引入完整 SSRF 面**，且绕过上游的合规边界 |
| N9 | Key 池 / 多 Key 轮换 | **QPS 是账号级**，同账号多 Key 无收益。⚠️ 原记载「实测 200 并发 0 次 429」**只对 search 成立**；2026-10-20 复测 fetch **60 并发即触发 28 次 429**，上游 message 自报 `Your current QPS: 25`（见 `Contract/23-上游能力实测报告` §6.1）。**阶段一不预留任何接口**（推测性抽象）。将来要加时：`deepseek.Config` 增加 `ApiKeys []string` + 私有 `nextKey()`，触发条件是「出现 2402 余额不足导致的服务中断且用户备有第二个账号」 |

## 五、阶段一内部的临时妥协（发布前必须复核）

> 🔴 **「必须复核」MUST 有闸门**：`Contract/17-版本与发布契约` §七 的发布检查单含一项「逐条复核本节 T1~Tn 并记录结论」，`Release.sh` 未通过则中止发版。没有闸门的「必须复核」等于没有复核 —— 本节此前只有约定、无检查项。

| # | 妥协 | 风险 | 复核条件 |
|:-:|---|---|---|
| T1 | `fetch.max_attempts` 默认 **2**（不是 3） | 慢站失败率略高 | 因为调用方 MCP 工具超时常见为 120s，`45000×3 + 退避` 会超时。若调用方超时 ≥180s，可调到 3 |
| ~~T2~~ | ~~Search 默认不缓存（`ttl_search_s=0`）~~ **已于 2026-10-20 关闭** | — | **立论被实测推翻**：同 query 连打 3 次 sha256 **全等**（`Contract/23-上游能力实测报告` §3.4），原记载的「4 次 12437/12437/12204/12490」在短窗口内不复现。⇒ `ttl_search_s` 默认改为 **180**，见 **ADR-014**。验证方式：23 号 §八 复现脚本第 2 项 |
| ~~T3~~ | ~~`truncated_by="upstream"` 是启发式判定~~ **已于 2026-10-20 关闭** | — | **立论被实测推翻**：并发同 URL 的**成功**响应内容 sha256 全等，原记载的「5 种长度 168K/231K/322K/428K」实为 **504 超时**（上游 fetch 网关 30s 硬超时）导致的失败，不是内容不确定；且 RFC 9110（437,738 rune、结尾正常）会被原启发式**误判为截断**。⇒ **删除字符数窗口启发式**，`truncated_by="upstream"` 仅在拿到确定信号时填写；504 走 2504 可重试路径。证据：23 号 §4.6、§4.7 |
| T4 | 日志轮转自研（~140 行） | 自研代码有 bug 风险 | `lumberjack` 只能按单文件大小轮转，**做不到「按自然日总量封顶」**。自研功能更窄反而更可控，但 MUST 有测试覆盖跨日切分 |
| T5 | 不实现 SSE 传输 | 真·SSE-only 客户端连不上 | MCP 2026-07-28 只定义 stdio 与 Streamable HTTP；HTTP+SSE 属 2024-11-05 且已 Deprecated。`Transport.Handler` 留作扩展点：新增传输 = 1 个文件 + 1 行配置 |
| T6 | 发布产物只有 `SHA256SUMS`，**无签名** | SUMS 与二进制同源发布，无身份证明，用户核对 SHA256 并不能证明来源 | 过渡措施：`release.yml` 给 `SHA256SUMS` 做 **cosign keyless 签名**（需 `id-token: write`）。彻底方案见 **DEBT-005**（SLSA L3） |
| T7 | `Release.sh` 直推 `main`（`git push origin main --follow-tags`） | 与 main 分支保护冲突（Scorecard 与社区规范通常要求禁直推） | 改为只 `git push origin v$VERSION`（tag），main 走正常 PR 流；或在 `30-部署运维手册` 写明分支保护的例外配置 |
