## ADR-001 实现语言选 Go

**状态**：已接受（2026-10-20）

### 背景

需要实现一个 MCP 服务器，同时支持 `stdio` 与**无状态 Streamable HTTP**（MCP 2026-07-28）。真实难点是：令牌桶限流、重试退避、跨进程 singleflight、并发抓取、SQLite 缓存——**全部是并发与 IO 调度问题**，不是算法问题。

候选：Go / Rust / Python / C / C++ / Node。

### 决策

**Go 1.27**。

### 理由（按权重排序）

| # | 理由 | 实测/事实依据 |
|:-:|---|---|
| 1 | **官方 SDK 一条配置项就切到 2026-07-28 无状态模式** | `mcp.StreamableHTTPOptions{Stateless: true}`，实测 `server/discover` 返回 `supportedVersions[0] = "2026-07-28"` |
| 2 | **单一静态二进制** | `CGO_ENABLED=0` 编译出 ~9MB 无依赖文件。SQLite 用 `modernc.org/sqlite`（纯 Go）保住这一点 |
| 3 | **并发模型与问题同构** | 限流/重试/singleflight 用 goroutine + `golang.org/x/time/rate` 表达最短 |
| 4 | **部署零负担** | 客户端只需在配置里写一个路径，不需要 pip/npm/venv/运行时 |
| 5 | **交叉编译开箱即用** | `GOOS/GOARCH` 四个目标一次编完，不需要交叉工具链 |
| 6 | **强类型 + 严格 JSON tag** | 上游**静默忽略未知字段**（实测），强类型 struct 能在编译期抓住拼错的键名 |

### 放弃的选项

| 语言 | 强项 | 为什么放弃 |
|---|---|---|
| **Rust** | 性能与内存安全最强 | ① 无成熟官方 MCP SDK（社区版要自己跟规范）；② 异步 + 生命周期在「限流+重试+缓存」这类胶水代码上会显著拖慢迭代；③ 交叉编译要装 target + linker，部署侧复杂度上升。**收益（性能）不是本项目瓶颈**（QPS 上限 60） |
| **Python** | 生态最全、写最快 | ① 部署要 Python 运行时 + venv + 依赖，与「单二进制」目标冲突；② 要在 stdio 下同时做并发抓取，`asyncio` + SDK 的协作要额外设计；③ 类型提示不强制，上游字段拼错只能运行时发现 |
| **C / C++** | 极致控制 | ① 没有 MCP SDK，TLS/HTTP/JSON/SQLite 全部要自己接；② 内存安全风险；③ 开发成本是 Go 的 5~10 倍。**本项目没有一处需要 C 级控制**（不做二进制解析、不做零拷贝流处理） |
| **Node/TS** | SDK 支持好 | 运行时依赖 + `node_modules` 体积，且 TS 的类型在运行时不存在 |

### 后果

| 正面 | 负面 |
|---|---|
| 一个文件扔到机器上就能跑 | 团队若不熟 Go，学习成本在并发与错误处理习惯上 |
| 官方 SDK 跟进规范演进 | 受 SDK 版本约束（已登记 DEBT X1） |
| `-race` 能直接抓并发 bug | 二进制比 C 版大（~9MB） |

### 重新考虑的条件

- 官方 SDK 长期停止维护且无替代 → 考虑 Rust 社区 SDK 重写
- 需要做二进制协议解析或极低延迟转发 → 该部分单独用 Rust/C 写 so 或 subprocess

## ADR-002 传输协议：stdio + 无状态 Streamable HTTP，不做 SSE

**状态**：已接受（2026-10-20）

### 背景

用户要求实现三种协议：① stdio；② 2026 年最新规定的无状态 Streamable HTTP；③ 为兼容老客户端的 SSE。

### 决策

实现 ① 与 ②。**③ 不实现传输层 SSE**，改用两条替代路径：

1. **实测验证**：老客户端（2024-11-05 / 2025-03-26 / 2025-06-18 / 2025-11-25）在**无状态 Streamable HTTP 端点**上全部能完成握手与 `tools/call`。它们要的不是 SSE 传输，而是「能连上」。
2. **配置级兼容**：`server.http.json_response = false` 时返回 `text/event-stream`（Streamable HTTP 规范内允许的响应形态），覆盖「只认 SSE 响应格式」的客户端。
3. **留扩展点**：`Transport.Handler` 接口，将来真要 HTTP+SSE 传输 = 1 个新文件 + 1 行配置，`domain`/`deepseek`/`tools` 一行不动。

### 理由

| 事实 | 来源 |
|---|---|
| MCP `2026-07-28` 规范**只定义** stdio 与 Streamable HTTP 两种 binding | 规范原文 changelog |
| HTTP+SSE 传输属 `2024-11-05`，**已列入 Deprecated**，有 12 个月下线期 | 规范 changelog |
| `go-sdk` 的 `NewSSEHandler` **误导性宣称**支持 2026-07-28 | SDK issue #1112 |
| 4 个历史版本客户端在无状态端点上全部 `[OK]` | 本项目实测（SDK 客户端 5 组场景） |

### 放弃的选项

| 选项 | 为什么放弃 |
|---|---|
| 用 go-sdk 的 `NewSSEHandler` 真做 SSE 传输 | 它会对外宣称支持 2026-07-28 但实际不完整 → 自己造一个「看起来新、实际旧」的端点，比不做更糟 |
| 自己做 HTTP+SSE 的协议转换层（POST 收 + GET 回） | 要多维护一套会话状态机，而收益只覆盖极少数客户端。MCPMesh 网关可以做协议转换 |

### 后果

| 正面 | 负面 |
|---|---|
| 只需维护 2 个传输实现 | 真·SSE-only 客户端（只支持 2024-11-05 GET 长连接的）连不上 |
| 不会因依赖废弃规范而在半年后重写 | 需要在 README 里明确说明这个限制 |
| `json_response=false` 已覆盖大部分「SSE 响应格式」需求 | — |

### 重新考虑的条件

- 出现明确用户反馈：「某客户端连不上，且确认它只支持 HTTP+SSE 传输」
- MCP 规范撤销 Deprecated 决定（极不可能）

## ADR-003 Streamable HTTP 只做无状态，不提供 `mode` 开关

**状态**：已接受（2026-10-20）

### 背景

`StreamableHTTPOptions.Stateless` 是个 `bool`。直觉上想「默认无状态，配置可切有状态」，兼容性最好。

### 决策

**只做无状态，配置里不出现任何 `mode` / `stateless` 字段。**

### 理由

| 事实 | 说明 |
|---|---|
| `Stateless = false` **不启用任何能力** | 它只是**移除** 2026-07-28 支持。设成 false 等于「倒退到旧协议」，不是「多一种模式」 |
| 无状态端点已覆盖有状态客户端的全部需求 | 实测 legacy 客户端在无状态端点全流程通过 |
| 我们没有任何需要跨请求会话状态的功能 | 两个工具都是无状态请求-响应；缓存走 SQLite，不在内存会话里 |
| 多一个开关 = 多一组配置组合要测 | 4 个传输 × 2 个模式 = 8 种组合，实际只需要 2 种 |

### 后果

| 正面 | 负面 |
|---|---|
| 配置项少一个，测例少一半 | 无法提供「有状态 Streamable HTTP」给需要它的客户端 |
| 协议行为一致，不会「同一个二进制在不同配置下支持不同协议版本」 | — |

### 重新考虑的条件

出现需要**服务端主动推送**的能力（如长任务进度、订阅式更新）。那种能力必须先有会话状态。

## ADR-004 配置格式 `config.toml` + `Config/.env`（仅密钥）

**状态**：已接受（2026-10-20）

### 背景

需要选配置格式，并把敏感信息分离。

### 决策

| 文件 | 内容 | 权限 |
|---|---|---|
| `Config/config.toml` | 全部**非敏感**配置 | 644 |
| `Config/.env` | **只有** `DEEPSEEK_API_KEY` + 可选 `DEEPSEEKSEARCH_HTTP_TOKEN` | **600** |

优先级：`环境变量 > Config/.env > config.toml > 内置默认值`。

### 为什么 TOML 不用 YAML

| YAML 的问题 | TOML 的处理 |
|---|---|
| **Norway 问题**：`country: NO` 被解析成布尔 `false` | 所有值有显式类型，`"NO"` 就是字符串 |
| 隐式类型推断：`1.0` / `1e3` / `010` 行为不一致 | 整数/浮点/日期语法严格分离 |
| 缩进地狱：层级靠空格，粘错一格就换父节点 | 显式 `[section.subsection]`，不依赖缩进 |
| 多行字符串的 `\|` `>` 语义反直觉 | 三引号 + 转义规则简单 |
| 重复键静默覆盖（部分实现） | 标准明确规定重复键是错误 |

### 为什么密钥必须分离

| 理由 | 说明 |
|---|---|
| `config.toml` 会被复制/贴到 issue/发给朋友排查 | 密钥在里面的必然结局是泄漏 |
| 权限模型不同 | 644 可读 vs 600 只有属主可读。合在一起就只能全 600，配置就不方便查看 |
| 启动强制检查 | ① `config.toml` 出现 `key`/`token`/`secret`/`password`/`credential` 类键名 → **拒绝启动**并打印行号；② `.env` 权限非 600 → 拒绝启动 |
| 换 Key 不用改主配置 | 只需要改 `.env` 一行 |

### 放弃的选项

| 选项 | 为什么不用 |
|---|---|
| 全部放 `.env` | 60+ 个配置项塞 `.env` 没有层级结构，无法表达数组/嵌套 |
| 全部放 `config.toml`（含密钥） | 见上，必然泄漏 |
| YAML | 见上四条 |
| JSON | 不能写注释。配置项「选了会怎样」必须能就地注释 |
| 环境变量优先（12-factor） | 60 个环境变量在 systemd 里不可维护；且数组类配置（`fixed_ms = [1000,3000,8000]`）在环境变量里难表达 |

### 后果

| 正面 | 负面 |
|---|---|
| 配置可读、可注释、可版本控制（`config.toml` 的一部分可以提交成 `config.example.toml`） | 需要维护两套解析路径 |
| 未知键拒绝启动 → 拼错的参数当场暴露 | 每次加参数要同步 4 处（struct / toml / 文档 / 测试） |

## ADR-005 搜索语法：透传 + 结构化字段 + `raw_query` 逃生口（C 方案）

**状态**：已接受（2026-10-20）

### 背景

DeepSeek Search 支持 `site:` `-site:` `"精确短语"` `lang:zh,en` `after:2025` `before:2026` 等**行内语法**。MCP 工具该怎么暴露？

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 纯透传 | 只有 `query` 一个字符串参数，语法全交给调用方拼 | 最简单，零歧义 | 模型容易拼错；拼错了上游**不报错**，静默返回无关结果（实测） |
| B 纯结构化 | 只有 `site[]` `lang[]` `after` 等字段，内部拼装 | 类型安全 | 无法表达上游支持的全部语法组合；新语法要改代码 |
| **C 混合** | `query` 透传 + 结构化字段可选 + `raw_query=true` 完全绕过 | 兼顾 | 参数多，需要讲清优先级 |

### 决策

**C 方案**。

```go
// ds_search 的语法相关参数
Query        string   // 透传，原样
Site         []string // 拼成 site:a.com OR site:b.com
ExcludeSites []string // 拼成 -site:c.com
Lang         []string // 拼成 lang:zh,en
After        string   // 拼成 after:2025
Before       string   // 拼成 before:2026
ExactPhrase  string   // 拼成 "短语"
ExcludeTerms []string // 拼成 -"项"
RawQuery     bool     // true 时完全绕过以上拼装
```

响应**必带** `query_effective`（实际发给上游的字符串）+ `warnings[]`（软校验告警）。

### 关键设计点

| 点 | 决策 | 理由 |
|---|---|---|
| `query` 内已含同名操作符 + 同时传了结构化字段 | **不重复追加**，记入 `warnings[]` | 重复追加会得到 `site:a.com site:b.com` 这种上游只认第一个的串 |
| 拼装后总长 > 128 rune | **本地拒绝**（`1090`），不发请求 | 省一次 12 秒的往返与「白等」 |
| 未知语言码 | **只警告不拒绝** | 上游对 `lang:xx` 是软校验，我们硬拒会误伤 |
| 日期格式 | 本地正则硬校验 `^\d{4}(-\d{2}-\d{2})?$` | 格式错上游会静默忽略整个操作符 |

### 为什么必须有 `query_effective`

**实测：上游对语法零校验。** 写 `site:不存在的域名` 返回 200 + 一堆不相关结果，不报错。所以唯一能帮调用方发现问题的手段，就是回报「我实际发出去的是什么」+「我怀疑哪里有问题」。

### 后果

| 正面 | 负面 |
|---|---|
| 模型用简单方式（只传 query）就能工作 | `ds_search` 有 18 个参数，`tools/list` 的 schema 较长（~1.2k token） |
| 需要精确控制时能用结构化字段 | 拼装逻辑要 ~8 个测试用例覆盖 |
| `raw_query` 保底，任何我们没预料到的语法都能用 | 两个入口（拼装 / 绕过）容易出现行为不一致，靠 `query_effective` 对齐 |

### 重新考虑的条件

上游新增操作符 → 加结构化字段，不改架构。

## ADR-006 缓存后端用 SQLite，不用内存

**状态**：已接受（2026-10-20）

### 背景

`ds_fetch` 的 TTL 设 6 小时能显著省钱。缓存放哪？

### 决策

**SQLite 持久化**（`modernc.org/sqlite`，纯 Go 无 CGO）。表结构含 `cache` + `inflight` 两张。

### 理由（决定性的一条）

| 场景 | 内存缓存 | SQLite 缓存 |
|---|---|---|
| **stdio 模式**（默认） | 每个客户端各起一个进程 → **3 个客户端 = 3 份隔离缓存 = 0 跨客户端共享** | 三个进程共享同一个 `Data/Cache.db` |
| 进程重启 | 全丢 | 保留 |
| 跨进程 singleflight | **不可能实现** | `inflight` 表可做租约 |
| 崩溃恢复 | 不可用 | WAL 模式可恢复 |

🔴 **决定性事实**：`stdio` 是 MCP 最常见的部署形态，而它**一客户端一进程**。选内存缓存等于在最主流的场景下缓存完全失效。

### 补充实测依据

- 同一 URL **并发**冷请求 5 次 → 返回 5 种不同长度（168K/231K/322K/428K/429K）→ **上游不合并并发请求，5 并发 = 5 次计费**。这让 `inflight` 表从「优化」升级为「必需」。
- Search 返回的 URL 大量带 `utm_*`，上游缓存被 utm 参数击穿（`?utm_source=x` → 3.78s 重新抓取）→ 我方按规范化 URL 缓存是唯一有效省钱层。

### 表结构（MUST 逐字使用）

```sql
-- cache 存上游正文快照。body 是上游原文，MUST NOT 存反转义后的内容。
CREATE TABLE IF NOT EXISTS cache (
    capture_id TEXT PRIMARY KEY,   -- 一次具体抓取的 ID，绑定快照语义
    kind       TEXT NOT NULL,      -- 'search' | 'fetch'
    canonical  TEXT NOT NULL,      -- 规范化后的 key（URL 或 query 的 hash）
    body       BLOB NOT NULL,
    nbytes     INTEGER NOT NULL,
    created_at INTEGER NOT NULL,   -- unix 秒
    expires_at INTEGER NOT NULL,   -- unix 秒；0 = 永不过期（不使用）
    hits       INTEGER NOT NULL DEFAULT 0,
    last_hit_at INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_cache_canonical ON cache(canonical, kind);
CREATE INDEX IF NOT EXISTS idx_cache_expires   ON cache(expires_at);

-- inflight 是跨进程 singleflight 租约表，防重复计费。
CREATE TABLE IF NOT EXISTS inflight (
    k               TEXT PRIMARY KEY,
    owner           TEXT NOT NULL,      -- 进程标识 hostname:pid:startupUnixNano
    expires_at      INTEGER NOT NULL,
    last_error_code INTEGER NOT NULL DEFAULT 0  -- owner 失败时写入，见下方修订说明
);
```

**修订（2026-10-20）**：原表只有 `k/owner/expires_at` 三列，无法表达「owner 失败了」这件事。进程内等待者靠 `map[string]*call` 拿到同一个 error 对象，但跨进程等待者只能看到「租约消失且缓存无值」，与「owner 崩溃」不可区分 —— 它只能返回 `3075`，而 `3075` 的语义是「等待超时」，不是「上游失败」。故增列 `last_error_code`：owner 执行失败时**先写这一列再删租约**，跨进程等待者据此把 owner 的真实错误码放进 `details.owner_error_code`。详见 `Tasks/Task-07-缓存与跨进程singleflight.md` §A-02 第 7/7.1 条。

PRAGMA（MUST 在打开连接后立即执行）：

```sql
PRAGMA journal_mode = WAL;      -- 读写不互斥
PRAGMA synchronous  = NORMAL;   -- 崩溃最多丢最后一个事务，缓存场景可接受
PRAGMA busy_timeout = 5000;     -- 多进程写冲突时等 5s 而非立即失败
PRAGMA temp_store   = MEMORY;
```

### 后果

| 正面 | 负面 |
|---|---|
| 跨进程/跨重启共享 | 需要管 `Data/Cache.db` 的清理与体积上限 |
| singleflight 可跨进程 | 多一次磁盘 IO（本地 SSD 上是微秒级，相对 12 秒的上游请求可忽略） |
| `:memory:` 可给测试用同一套代码 | 需要 `rowserrcheck`/`sqlclosecheck` 两个 linter 防资源泄漏 |

### 重新考虑的条件

若将来只做 `streamable-http` 单进程部署，且实测内存缓存命中率足够，可加一个 `backend = "memory"` 实现（但**默认仍是 sqlite**）。

## ADR-007 错误码三段位，2xxx 用 `2000 + http_status`

**状态**：已接受（2026-10-20）

### 背景

需要一个错误码体系：人能一眼看出「是我的错、上游的错、还是本地的错」，且能机器判定是否可重试。

### 决策

| 段位 | 含义 | 编号规则 | 数量 |
|:-:|---|---|:-:|
| **1xxx** | 我方入参校验 | 从 1000 起，**步长 10** | 11 |
| **2xxx** | 上游返回 | **`2000 + http_status`**（另有 3 个哨兵，见下） | 14 |
| **3xxx** | 本地资源/状态 | 从 3000 起，**步长 10**（另有 1 个哨兵） | 16 |
| | | **合计** | **41** |

> **本表数量已由 ADR-016（2026-10-20）修订**：原为 11/13/15、合计 39。新增 `2998 UP_NETWORK` 与 `3099 LOC_INTERNAL`。`Scripts/CheckConsistency.py` 会把本表与 `14-错误契约.md` §二 的实际条数做三方对账，改一处必须改两处。

### 为什么 2xxx 不按步长 10

步长 10 的价值是「留插入空间」。但上游的 `http_status` 是**天然连续枚举**（400/401/402/403/404/408/413/429/500/503/504），而且：

| 理由 | 说明 |
|---|---|
| **可推导** | 看到日志里的 `2429`，任何人立刻能反推「上游 429 限流」。看到 `2140` 还要查表 |
| **不会冲突新增** | 上游新增状态码（如未来 425）时，`2425` 天然可用，不需要重新排号 |
| **不需要插入空间** | 上游状态码本身稳定，不会「两个状态码之间再插一个」 |
| **对账友好** | 计费/日志分析时可以直接 `code - 2000` 得到 HTTP 状态 |

### 编号分配的机械规则

| 段位 | 公式 | 插入新码时 |
|---|---|---|
| 1xxx | `1000 + n*10` | n 顺延（1095 后是 1100） |
| 2xxx | `2000 + http_status` | 无需分配，随上游 |
| 3xxx | `3000 + n*10` | n 顺延（3093 后是 3100） |

### 错误体字段（数量由 8 修订为 9）

🔴 **结构体定义的唯一真源是 `Contract/14-错误契约.md` §三**，本 ADR MUST NOT 复制一份 Go struct —— 两处各写一份正是「字段顺序漂移」的生成机制（`Task-02` 曾声称与 14 号「逐字一致」，实际顺序不同）。

本 ADR 只记录**决策本身**：

| 决策 | 内容 | 修订 |
|---|---|---|
| 必带字段 | `code` / `name` / `message` / `hint` / `retryable` | 原写「前 4 项必带」，但 `retryable` 无 `omitempty` 恒出现 ⇒ 实为 **5 项** |
| 条件字段 | `upstream_http` / `upstream_msg` / `request_id` / `details` | `details` 由 **ADR-016 连带新增**（见 14 号 §3.0），承载 `queue_depth` / `retry_after_ms` / `cause` 等机器可读数值 |
| 字段顺序 | MUST 与 struct 声明顺序一致（`encoding/json` 按声明序输出），样例即契约 | 由 14 号 §三 钉死 |
| 为什么 `name` 是稳定契约 | 调用方（含 LLM）按 `name` 分支比按数字码可读；改名等同破坏契约，MUST 走 ADR | — |

### 为什么错误码表放 Resource 不放 description

| 位置 | token 成本 |
|---|:-:|
| 放进 `ds_search` 的 description | ~1,500 token / 每次 `tools/list` |
| 放进 MCP Resource `ds://error-codes` | 120 token（description 里只写 3 条行为规则） |
| **节省** | **92%** |

且模型按需读取 Resource，比每次都被塞一遍码表更合理。

## ADR-008 阶段一不做 Key 池，也不预留接口

**状态**：已接受（2026-10-20）

### 背景

直觉上多 Key 能提高吞吐、能在余额耗尽时切换。

### 决策

阶段一只支持**单个** `DEEPSEEK_API_KEY`。**不做** Key 池/轮换。但保留接口钩子。

**阶段一不写入任何 `KeyProvider` 接口。**

这一点是刻意收紧的：留一个没有人调用、也没有实现的接口，属于推测性抽象（见 `Engineering/20-编码规范` 的「禁止推测性编码」）。真要做 Key 池时，新增一个只被 `deepseek.New` 使用的 `Config.ApiKeys []string` + `nextKey()` 私有函数即可，约 20 行，不需要提前建抽象层。

将来引入 Key 池的**触发条件**与**做法**写在 `Decisions/16-技术债登记表` 的 `N9` 里。

### 理由

| # | 事实/推算 |
|:-:|---|
| 1 | **QPS 是账号级的**，不是 Key 级的。同账号多 Key 不提升上限 |
| 2 | 实测：200 并发 → **0 次 429**，约 26 QPS 跑通。官方文档写 5 QPS，是保守值 |
| 3 | 单 Key 60 rps × 3600s = **216,000 次/小时 = ¥1,080/小时**。一个 agent 的真实峰值是 2~5 QPS |
| 4 | 「余额耗尽切换」需要**第二个账号**，这是组织问题不是代码问题 |
| 5 | 多 Key 会引入「这个请求用了哪个 Key」的对账复杂度，阶段一没有收益只有成本 |

### 后果

| 正面 | 负面 |
|---|---|
| 少一个配置段、少一套并发安全逻辑 | 余额耗尽时只能报 `2402`，不能自动切换 |
| 对账简单：一个 Key，一份账单 | 将来加 Pool 需要新增 ADR |

### 重新考虑的条件

- 出现余额耗尽导致的服务中断（且用户备有第二个账号）
- 上游改为**按 Key 计 QPS**（`x-ratelimit` 头出现 key 维度）

## ADR-009 大文档返回：按标题分节（C 方案）+ 长度分级

**状态**：已接受（2026-10-20）

### 背景

`ds_fetch` 实测返回过 568,436 字符的正文（约 200k token），直接塞进上下文会**爆**。而且：

- 上游 Fetch **没有 `offset` 参数**（不像某些抓取 API 能续读）
- 上游会**静默截断**（100,165 / 166,359 / 568,436 三种长度，无标记）

| 方案 | 做法 | 问题 |
|---|---|---|
| A 硬截断 | 超过 N 字就砍 | 模型永远读不到后半部分，且不知道自己被砍了 |
| B 固定分块 + offset | 我们自己实现 offset | 分块边界随机落在句中；模型不知道「该取哪块」（它没读过全文） |
| **C 按标题分节** | 先返回目录（section id + 标题 + 字数），模型按需取节 | 无标题的纯文本要退回固定分块 |

### 决策

**C 方案 + 长度分级**：

| 模式 | 触发 | 返回 |
|---|---|---|
| `inline` | `content` ≤ `inline_max_chars`（默认 8000 rune） | 全文 |
| `outline` | `content` > 阈值且未指定 `section` | 目录 + 每节预览 |
| `section` | 指定了 `section` / `sections` | 指定节全文 |

`cache_id` **绑定一次具体抓取**（不是绑定 URL）：

| 场景 | 行为 |
|---|---|
| TTL 过期后重新抓取 | **新** `cache_id`，节序号可能完全不同 |
| 用旧 `cache_id` 请求 | `3080 LOC_SNAPSHOT_GONE` + 「该快照已过期，请重新 fetch」 |
| **MUST NOT** | 静默用新内容替代旧快照（会让模型以为读的是同一份文档） |

### 关键实现约束

| 约束 | 理由 |
|---|---|
| 只认 ATX 标题（`^#{1,6} `），**不认 Setext**（`===` 下划） | Setext 在正文里误判率极高 |
| 代码块（``` 围栏）内的 `#` **MUST NOT** 当标题 | 否则 Shell 脚本的注释会把文档切碎 |
| 切分按 **rune**，不按 byte | 中文 1 字 3 字节，按 byte 切会出 `�` |
| 无标题时按 `fixed_chunk_chars`（默认 8000 rune）均分，`id` 用 `c0/c1/...` | 与 `s0/s1/...` 区分来源 |
| 永不返回空 `sections` | 单节也必须有一条 |

### 为什么 `cache_id` 不绑 URL

如果 `cache_id` = URL 的 hash，那么「TTL 过期后重新抓」会得到**同一个** `cache_id` 但**不同内容**，模型引用 `s3` 时会读到完全不同的段落，且**无从察觉**。绑快照是唯一诚实的做法。

### 后果

| 正面 | 负面 |
|---|---|
| 上下文可控（先目录后按需取） | 长文档要多一次往返 |
| 引用可追溯（`s3` 在快照内恒定） | 快照过期要重新抓（会计费） |
| 短页面零额外成本 | 无标题文档的分节体验较差（模型只能看字数猜） |

## ADR-010 不做答案合成

**状态**：已接受（2026-10-20）

### 背景

很多搜索 API（Tavily 的 `include_answer`、Exa 的 `summary`、Perplexity 的 `answer`）会返回一段「已经合成好的答案」。直觉上这样最省 token：一次调用直接拿到答案。

### 决策

**不做**。只保留 `synthesize` 参数位，传 `true` 返回 `1095 VAL_SYNTH_DISABLED`。

### 理由

| # | 理由 |
|:-:|---|
| 1 | **调用方本身就是 LLM**，且它持有用户的完整上下文。我们的合成模型只看得到 `query`，**看不见意图**。用信息更少的模型去回答信息更多的模型，净效果是负的 |
| 2 | **销毁引用**。合成后的答案无法告诉用户「这句话来自哪个 URL」。用户要核实就只能重新搜一次 |
| 3 | **隐藏 prompt injection**。合成的中间层会把「忽略之前的指令」这类内容洗成通顺的句子，反而更难识别 |
| 4 | **多花一次模型成本**，且延迟增加 |
| 5 | 上游 `summary` 已经是 **query 定向摘要**（实测同一 URL 在三个 query 下给出 967 / 105 / 514 字）—— 它已经做了「按问题抽取」这件事，我们再合成一层是多余 |

### 替代方案（已实现）

| 手段 | 效果 |
|---|---|
| `detail` 四档分级（`minimal`/`snippet`/`summary`/`content`） | 调用方按需选择信息密度 |
| 默认 `detail=summary` + `summary_chars=1200` | 一次调用即可支撑回答，不必再 fetch（省一次 ¥0.005 与一次往返） |
| 三层去重（URL / 转载 / 域名配额） | 无损省 token |
| `ds_fetch` 分节 | 需要原文时精确取用 |

### 后果

| 正面 | 负面 |
|---|---|
| 引用完整、注入可见、成本最低 | 对「只想拿一句话答案」的调用方多一次自己合成的步骤 |
| 行为可预测 | 与部分竞品 API 形态不同 |

### 重新考虑的条件

- 用户明确要求，且接受「引用丢失」与「注入被洗白」两个代价
- 出现不需要引用的场景（如内部知识库问答）

## ADR-011 版本号编译期注入，首发 `v0.1.0`

**状态**：已接受（2026-10-20）

### 背景

需要「内建的版本号」：能 `--version` 查、能在 GitHub 上对 tag、能在 MCP 协议层体现、以后升级能对比。

### 决策

| 项 | 值 |
|---|---|
| 唯一真源 | `Makefile` 的 `VERSION := v0.1.0` |
| 注入方式 | `-ldflags "-X main.version=$(VERSION) -X main.commit=$(COMMIT) -X main.buildTime=$(BUILD_TIME)"` |
| 三处出口 | `--version` / `serverInfo.version` / `/healthz` |
| 首个版本 | **`v0.1.0`** |
| git tag | 附注 tag `v0.1.0` |

### 为什么注入而不是读配置

| 方案 | 问题 |
|---|---|
| 读 `config.toml` 的 `[app] version` | **配置描述环境，不描述二进制**。同一份配置可能被两个不同版本读取，此时版本号是假的 |
| 读 `debug.ReadBuildInfo()` | 能拿到模块版本，但 `go build` 本地构建时是 `(devel)`，无法表达 `v0.1.0` |
| **`-ldflags -X` 注入** | 版本号烧进二进制。`file` 一下就知道这是什么版本，不需要任何外部信息 |

### 为什么留 `[app] version` 兜底

开发机上 `go run ./cmd/...` 不经过 Makefile，注入值为 `v0.0.0-dev`。此时配置里的值能让人看出「这是哪个分支」。**但协议层永远用注入值** —— 判定逻辑 `EffectiveVersion` 见 `17-版本与发布契约` §四。

### 为什么首个版本是 `v0.1.0` 而不是 `v1.0.0`

| 理由 |
|---|
| 契约会随阶段二演进（`ds_research` / `ds_extract` / `no_cache` / `SKILL.md` 四项已登记为 DEBT-001~004） |
| `0.x` 阶段允许在 MINOR 里做参数删改，不需要升 MAJOR |
| 打 `v1.0.0` 会给人「接口冻结」的错误期待 |

### 后果

| 正面 | 负面 |
|---|---|
| 版本可追溯、可复现构建 | 发版必须走 Makefile，直接 `go build` 会得到 `v0.0.0-dev` |
| 三处版本号强制同源 | 需要 `TestEffectiveVersion` + 协议契约 P26 守住 |

## ADR-012 开源许可选 MIT

**状态**：已接受（2026-10-20）

### 背景

项目要公开发布到 GitHub，需要选一个许可。诉求是「最宽松」—— 让任何人可以商用、修改、闭源分发、再许可，作者不承担额外义务。

### 决策

**MIT**。

### 候选对比

| 许可 | 用户义务 | OSI 认可 | 中国法下的确定性 | 结论 |
|---|---|:-:|:-:|---|
| **MIT** | 保留版权声明与许可原文 | ✅ | 高（纯授权，不涉及放弃人身权） | **采用** |
| `0BSD` / `BSD-0-Clause` | **无**（连署名都不要求） | ✅ | 高 | 不采用：放弃署名对本项目没有收益（用户保留一行声明几乎零成本），反而失去溯源 |
| `Unlicense` / `CC0-1.0` | **无**（公有领域奉献） | ✅ / 半 | **低** —— 《著作权法》下著作人身权（署名权等）不可转让、不可放弃，公有领域奉献在国内可能被认定部分无效 | 不采用：法律不确定性换不到实际好处 |
| `Apache-2.0` | 保留声明 + NOTICE + 专利授权条款 + 变更声明 | ✅ | 高 | 不采用：比 MIT 严格，且要维护 `NOTICE` |
| `MPL-2.0` / `LGPL` / `GPL` | 传染（文件级 / 库级 / 项目级） | ✅ | 高 | 不采用：与「最宽松」直接冲突 |

### 为什么在「最宽松」里仍是 MIT

1. **中文语境里的「最宽松」默认指 MIT** —— 常见排序是 `MIT/BSD > Apache-2.0 > MPL > LGPL > GPL`。选 MIT 就是选这个共识位。
2. 严格意义上更宽松的 `0BSD` / `Unlicense` 省掉的只是「保留一行版权声明」这一项义务。对使用者几乎零成本，对作者却是唯一的溯源凭证 —— **收益不对称，不值得**。
3. `Unlicense` / `CC0` 依赖「放弃著作权」这一动作，而《中华人民共和国著作权法》第十条规定署名权等人身权**不可转让、不可放弃**。用 MIT 只是**授权**，法律路径最干净。
4. GitHub 建仓时一键可选，`LICENSE` 会被自动识别为 `MIT`，徽章、依赖扫描、SBOM 全部免配置。

### 后果

| 正面 | 负面 |
|---|---|
| 任何人可商用、闭源集成、再许可 | 别人拿走 MIT 代码后可以完全不开源，这是「宽松」的必然代价 |
| 无 NOTICE、无专利条款、无变更声明 | 不提供明示专利授权（Apache-2.0 才有） |
| 版权行固定 `Copyright (c) 2026 小逸 <https://github.com/LseKit/DeepSeekSearch>` | 版权行是唯一不可删的东西，必须写在 `LICENSE` 里 |
| 与依赖生态一致（全部 MIT/BSD/Apache 兼容） | — |

### 重新考虑的条件

- 出现专利诉讼风险，需要明示专利授权 → 换 `Apache-2.0`
- 要求下游必须开源 → 换 `GPL-3.0`（与「最宽松」诉求相反，需用户明确指示）
- 用户明确要求「连署名都不要」→ 换 `0BSD`（只需换 `LICENSE` 正文 + 改 README 徽章 + 本 ADR 追加一条）

> 改许可 = 改 `LICENSE` + `README` 徽章与末段 + `CHANGELOG` 记一条 + 本 ADR 追加决策。`grep -rn 'MIT' docs/ README.md` 可列出全部触点。

## ADR-013 Markdown 反转义字符集扩到实测全集 32 个

**状态**：已接受（2026-10-20）
**证据**：`Contract/23-上游能力实测报告.md` §4.5

### 背景

上游 fetch 返回的是 Markdown 正文，其中大量标点被反斜杠转义。原设计（`12-数据契约` §6.1、`Task-02` A-02）记载「上游把 **11 个** Markdown 字符全加反斜杠」，正则为：

```go
var unescapeRe = regexp.MustCompile(`\\([/#.,:{}()\-!])`)
```

并以「一份 600KB 文本里有 15,582 个反斜杠」作为实测依据，验收断言写的是「`Unescape` 正则**恰好** 11 个字符」。

2026-10-20 对 7 个真实页面（DeepSeek-V3 README、go.dev/blog、arxiv、CSDN、MDN、百度、stackoverflow）做全量 `\\(.)` 统计，得到 **32 种**被转义字符。原 11 个全部被观测到（无多余项），但**缺了 21 种**，其中高频缺失项：

| 缺失字符 | 出现次数 | 破坏什么 |
|---|---|---|
| `\|` | 480 | **Markdown 表格彻底不可读**（比原表内的 `(`438、`)`444 还多） |
| `\*` | 382 | 粗体/斜体/列表标记 |
| `\=` | 338 | 代码（`torch\=\=2\.4\.1`） |
| `\;` | 223 | 代码 |
| `\'` | 197 | 英文所有格（`DeepSeek\'s`） |
| `\+` | 167 | 代码（`C\+\+`） |
| `\_` | 140 | **标识符与函数名**（`How\_to Run\_Locally`） |
| `\[` `\]` | 97 / 98 | 链接、数组下标 |
| `\<` `\>` | 90 / 74 | 代码（`\<script\>`） |
| `\"` | 74 | 引号、代码 |
| `\%` `\?` `\&` `\@` `` \` `` `\~` `\$` `\^` | 67 / 62 / 42 / 37 / 12 / 7 / 5 / 2 | 代码与 URL |
| `\\` | 26 | **嵌套转义**（见下） |

对一个面向开发者的搜索/抓取工具，`\_` 破坏标识符、`` \` `` 破坏行内代码、`\|` 破坏表格，都是**直接损害核心用途**的缺陷。

### 决策

1. **字符集扩到实测全集 32 个**：

```go
// unescapeRe 覆盖 23 号报告 §4.5 实测的 32 种被转义字符。
// 单趟替换：MUST NOT 用字符循环多次 ReplaceAll（见下方嵌套转义）。
var unescapeRe = regexp.MustCompile(`\\([/#.,:{}()\-!*|=_;\[\]<>"%?&@` + "`" + `~$^\\])`)

func Unescape(s string) string { return unescapeRe.ReplaceAllString(s, "$1") }
```

2. **MUST 单趟正则替换，MUST NOT 按字符循环**。实测存在 26 处嵌套转义（原文已含 `\.`，上游再转义一层成 `\\\.`）：
   - 单趟：`\\\.` → `\.`（正确，只脱一层，保留原文语义）
   - 多趟循环：`\\\.` → `\.` → `.`（**过度反转义**）

3. **保留白名单思路，MUST NOT 无脑删除所有反斜杠**。代码块里的 `\n`、`\d`、`\w` 是字面量，删掉会毁掉代码。实测 search 侧的 content 里就有 6 处 `\n`（§4.5.2）。

4. **🔴 `Unescape` 只允许用于 fetch 的正文路径**。实测证明 search 的 `content`/`snippet`/`summary`/`title` **完全不转义**（§4.5.2），对其调用 `Unescape` 会把代码里的 `\n` 变成字母 `n`。

5. 验收断言由「恰好 11 个字符」改为「**恰好 32 个字符**，且与 23 号 §4.5 的表格一致」。

### 放弃的选项

| 选项 | 为什么不选 |
|---|---|
| 通用规则「反斜杠 + 任意标点一律还原」 | 需要区分代码块与正文，得做 Markdown 结构解析；复杂度显著上升，且可能误伤正则示例（如正文里真的想展示 `\.`） |
| 只补高频缺失项（`\| \* = _ ' + ;`） | 省下的工作量很小，但 `` \` `` `\[` `\]` `\<` `\>` 仍会污染代码片段 —— 半修比不修更难排查 |
| 保持 11 个不动 | 表格与标识符损坏是**用户可见的正确性缺陷**，不是风格问题 |

### 后果

| 正面 | 负面 |
|---|---|
| 表格、粗体、行内代码、标识符全部正常 | 字符集变大后，若正文里**本就有** `\%` 这类字面量会被误还原（Markdown 语义下无法区分，可接受） |
| 单趟替换正确处理嵌套转义 | 正则字符类里的 `` ` `` 需要字符串拼接，写法略丑（Go 反引号字符串不能含反引号） |
| 与 search 侧的禁用规则明确分开 | 增加一条「哪些字段能 Unescape」的约束，需要测试守住 |

### 重新考虑的条件

- 上游改用标准 CommonMark 转义规则（只转义 ASCII 标点中的一部分）→ 重新实测并收缩字符集
- 出现「正文里的字面 `\%` 被误还原」的真实用户报障 → 改为带代码块识别的两阶段方案
- 上游修复转义行为、不再过度转义 → 可整体删除 `Unescape` 与 `unescape` 参数

> 触点：`12-数据契约` §六、`Task-02` A-02（含验收断言）、`Task-09`（调用点）、`Scripts/CheckConsistency.py`（字符数检查）。

## ADR-014 搜索结果缓存 TTL 由 0 改为 180 秒

**状态**：已接受（2026-10-20）
**证据**：`Contract/23-上游能力实测报告.md` §3.4

### 背景

`13-配置契约` 原定 `[cache] ttl_search_s = 0`（即**不缓存搜索结果**），理由记载为：

> 实测 Search 结果非确定性（4 次 12437/12437/12204/12490），缓存的失真不可被察觉

`Task-08` 亦以「上游同 query 结果非确定性」作为缓存默认关的理由。

2026-10-20 复测：同一 query `DeepSeek V3 架构`（`count=5`）**连续 3 次**调用，响应 **16,962 bytes、sha256 三次全等**（`7033165dacd8`），URL 列表与顺序完全一致。

⇒ 原立论在**短窗口内不成立**。观测到的字节数差异应来自跨小时/跨天的索引更新，而非请求间的随机性。

值得注意的是，原理由的后半句「缓存的失真不可被察觉」其实**支持**缓存而不是反对：如果失真不可察觉，那么短 TTL 缓存的代价就接近于零。

### 决策

`[cache] ttl_search_s` 默认值 **0 → 180**（3 分钟）。

理由：
1. **省钱是这个项目的核心诉求之一**（`Task-07`：「缓存定位『省钱不是功能』」）。搜索 ¥5/1000 次，一个 agent 在调试或迭代 prompt 时会反复用相同 query 搜索 —— 180s TTL 能直接吃掉这部分重复计费。
2. **180s 的新鲜度损失可忽略**：搜索引擎索引本身不会在 3 分钟内变化到影响结论；而 `ds_search` 的定位是「找资料」而非「监控实时事件」。
3. **仍可关闭**：需要严格新鲜度的用户设 `ttl_search_s = 0` 即恢复原行为。
4. **与 fetch 的 21600s（6 小时）形成合理梯度**：网页正文比搜索结果列表稳定得多。

配套约束：
- 命中缓存时响应 MUST 带 `from_cache=true`、`cached_at`、`age_seconds`、`saved_billed_calls`（这些字段 `12-数据契约` 已定义）。
- 命中缓存 MUST **不经过限流器占用上游配额**但仍计入本地 `max_inflight`（避免缓存击穿时打爆上游）。
- `age_seconds > ttl_search_s` 的条目 MUST 视为未命中并删除。

### 放弃的选项

| 选项 | 为什么不选 |
|---|---|
| 保持 0（不缓存） | 放弃了确定性的省钱收益，而立论已被实测推翻 |
| 更长 TTL（如 3600） | 搜索结果对时效性 query（新闻、价格、版本发布）敏感度高于网页正文；1 小时会让「最新版本」类查询拿到过期列表 |
| 按 query 分类设不同 TTL | 阶段一不做推测性抽象（同 ADR-008 的原则）；分类规则本身不可靠 |

### 后果

| 正面 | 负面 |
|---|---|
| 重复 query 零计费、零延迟 | 3 分钟内的结果可能略微过期 |
| 与 singleflight 叠加，进一步压低并发重复计费 | 缓存条目增加 ⇒ `Data/Cache.db` 增长（受 `max_bytes_mb=256` 约束） |
| 用户可用 `ttl_search_s=0` 完全关闭 | 需要在 CHANGELOG 与 README 说明默认行为 |

### 重新考虑的条件

- 出现「同一 query 在 60s 内返回不同结果」的可复现证据 → 降回 0 或改为「仅缓存 `count<=5` 的查询」
- 上游推出带时间戳的索引版本号（可判断是否变化）→ 改为按版本号失效而非 TTL
- 用户报障集中在「搜索结果过期」→ 降到 60

> 触点：`13-配置契约` `[cache].ttl_search_s` 及其理由表、`Task-07`、`Task-08`（调用链与测试）、`README` 已知限制、`CHANGELOG`。

## ADR-015 上游探活改用 `GET {base}/v1/tools/search` 期望 405

**状态**：已接受（2026-10-20）
**证据**：`Contract/23-上游能力实测报告.md` §二

### 背景

`Task-05` 原定「`Ping` 只 `GET /`（或 HEAD），不打计费端点」。`Task-10` 的 `ds_health` 依赖 `Client.Ping` 实现 `upstream_reachable` 检查，且同一文档内对「probe_upstream 是否计费」有互相矛盾的两种说法（`:33` 说会计费、`:47` 说不计费）。

2026-10-20 实测四个候选：

| 请求 | 结果 | 可用性 |
|---|---|---|
| `GET /` | **404，空 body** | ❌ 无法区分「网络通但 `base_url` 配错」与「路径不存在」—— 而 `base_url` 配错恰是最常见的部署事故 |
| `GET /v1/tools/search` | **405，空 body** | ✅ 走的是真实业务路由 |
| `HEAD /v1/tools/search` | 405 | ⚠️ 部分代理/CDN 会改写 HEAD 语义 |
| `GET /v1/models` | **200 + 模型列表** | ⚠️ 免费，但属 chat 侧端点，依赖 Key 有 chat 权限；受限 Key 会**误报不可达** |

### 决策

**`Client.Ping` 发 `GET {base_url}/v1/tools/search`，把 HTTP 405 判定为健康。**

判定表：

| Ping 结果 | 含义 | ds_health 的 `upstream_reachable` |
|---|---|---|
| **405** | 链路健康、路由正确 | `ok=true` |
| **401** | 链路通、Key 失效或缺失 | `ok=false`，detail 指向 3040/2401 |
| **404** | 链路通但 **`base_url` 或路径配错** | `ok=false`，detail 明确提示检查 `upstream.base_url` |
| 其它 4xx/5xx | 上游异常 | `ok=false`，带上游状态码 |
| 网络错误 / 超时 | 不可达 | `ok=false`，带 2998 |

**计费口径**：405 ≠ 200 且响应体为空，按 README 承诺的「HTTP 200 且拿到内容才计费」**不计费**。⇒ `Task-10:33` 的「会计费」说法 MUST 删除，`:47` 的「不计费」保留。

### 放弃的选项

| 选项 | 为什么不选 |
|---|---|
| `GET /` | 404 空体没有诊断价值，无法区分 base_url 配错 |
| `GET /v1/models` | 依赖 Key 的 chat 权限；本项目只需 tools 权限，用 chat 端点探活会在受限 Key 上误报 |
| `HEAD /v1/tools/search` | 实测同样返回 405，但 HEAD 在 CDN/代理链路上语义不稳定（上游是腾讯 EdgeOne，见 23 号 §5.2 的响应头） |
| 真实发一次最小 search（`count=1`） | 会计费，违反 `ds_health` 的「MUST NOT 发起任何计费请求」铁律 |

### 后果

| 正面 | 负面 |
|---|---|
| 免费、零副作用 | 依赖「上游对 GET 返回 405」这一行为；若上游改成返回 200 或 404，判定会失准 |
| 能诊断 `base_url` 配错（404 vs 405 的区别） | 判定逻辑比「status == 200」复杂，需要测试覆盖 4 个分支 |
| 走真实路由，能验证 TLS/SNI/CDN 全链路 | — |
| 解决 `Task-10` 的计费矛盾 | — |

### 重新考虑的条件

- 上游对 `GET /v1/tools/search` 的响应码改变（不再是 405）→ 重新实测四个候选并更新本 ADR
- 上游提供官方的免费健康检查端点 → 直接换用
- 需要验证 Key 有效性（不只是链路可达）→ 增加一次 `count=1` 的真实 search，但 MUST 在 `ds_health` 的 description 里明确警告会计费，并默认关闭

> 触点：`Task-05`（`Ping` 实现与测试）、`Task-10`（`:33`/`:47` 矛盾、`upstream_reachable` 判定标准）、`11-接口契约`（`Client` 接口注释）、`30-部署运维手册`（故障排查表补「Ping 得到 404 ⇒ base_url 配错」一行）。

## ADR-016 补 `2998 UP_NETWORK` 与 `3099 LOC_INTERNAL`（码表 39 → 41）

**状态**：已接受（2026-10-20）

### 背景

审计发现 `14-错误契约.md` 的错误码体系有**两处链路断裂**，二者都不会被任何护栏脚本拦住，只会在生产环境以最迷惑人的方式表现。

**断裂一：网络层错误永远不会被重试。**

`codeForStatus(httpStatus)` 是 2xxx 段的唯一入口，但一整类失败**根本不产生 HTTP 响应**：DNS 解析失败、TCP 连接被拒、TLS 握手失败、单次尝试超 `per_attempt_ms`（我方 ctx 到期）、响应读到一半连接断开。

这些错误以裸 `net.Error` / `context.DeadlineExceeded` 形式上抛，`ToPayload` 无从识别，落入唯一兜底 **`2999 UP_PARSE`** —— 而 2999 标记 **❌ 不可重试**。

于是 `14-错误契约.md` §六 可重试判定表里那一行「网络层错误：连接重置 / DNS 失败 / TLS 失败 / 读到一半断开 → ✅」**在实际代码路径上永远不可能被执行**。契约承诺了一个不存在的分支。

**断裂二：我方程序自身的 bug 被归因为「上游解析失败」。**

`2999 UP_PARSE` 的语义是「上游返回 200 但响应体不合契约」，是**外部问题**。但作为唯一兜底，它也吃下了「nil 被误传」「类型断言失败」「走到了 `default:` 分支」这类**内部缺陷**。运维看到 2999 会去查上游 API 变更，而真正该看的是自己的调用栈。排查方向被系统性带偏。

**加重因素**：这两处都不是「设计取舍」，是**遗漏** —— §六 表里明明写了网络错误可重试，说明设计意图存在，只是没有码来承载它。

### 决策

| 新码 | name | Retryable | 承载什么 |
|:-:|---|:-:|---|
| **2998** | `UP_NETWORK` | ✅ | 一切「拿不到 HTTP 响应」的失败。细分成因放 `details.cause` ∈ {`dns`, `tcp_connect`, `tls_handshake`, `attempt_timeout`, `response_reset`}，另带 `details.attempt` |
| **3099** | `LOC_INTERNAL` | ❌ | 兜底：不属于任何已知类别的错误（同一输入必然复现 ⇒ 重试无用）。`hint` 引导带 `call_id` 报 issue |

**`ToPayload` 的兜底判定 MUST 按此顺序**（先命中先返回）：

```
1. err 实现 domain.Coded（有 Code()）        → 用该码
2. errors.As 得 *UpstreamError               → codeForStatus(status)；status==0 时用 2998
3. net.Error / context.DeadlineExceeded
   / io.ErrUnexpectedEOF / io.EOF            → 2998
4. 其余一切                                  → 3099
```

**2999 被收窄为单一成因**：HTTP 200 且 `json.Unmarshal` 或字段校验失败。

**位置说明**：2998 位于 2999 之前**不违反** §七「MUST NOT 插进已有码之间」—— 2999/3099 是段尾**兜底哨兵**，不是有序序列成员；2998 是 2xxx 段最后一个具名新块。

**连带修正**：熔断器 `Record` 的失败判定同步收紧（`14-错误契约.md` §6.1）。原「`err != nil` 即记失败」会让本地限流拥塞（3000）累积成「上游熔断」，之后全部返回 3030 —— 自我实现的故障放大。改为**只有 `2408` `2429` `2500` `2503` `2504` `2998` `2999` 计入**。

### 放弃的选项

| 选项 | 为什么不选 |
|---|---|
| 每种网络错误一个码（DNS/超时/重置分开） | 对调用方毫无行动差异（都是「稍后重试」），只会让码表膨胀且 `Should` 的判定表变长。细分放 `details.cause` 即可 |
| 把网络错误归到 3xxx（本地资源段） | 语义错位：3xxx 的定义是「我方资源/限流/缓存状态」，而 DNS 失败是**出网链路**问题。且 `2000+http_status` 规则下 2xxx 段尾本就留给「上游交互异常」 |
| 让 2999 变成可重试 | 破坏契约：2999 是「上游 200 但内容不合契约」，同一请求重试大概率仍然解析失败，重试只会重复计费 |
| 不加 3099，只加 2998 | 断裂二依然存在，我方 bug 继续被误诊为上游问题 |
| 用 `errors.Is(err, context.DeadlineExceeded)` 直接映射到 3020 | 3020 是**整链总预算**超时（`total_timeout_ms`），而单次尝试超时（`per_attempt_ms`）是**可重试的**、且还有剩余尝试次数。二者混用会让「第 1 次尝试超时」直接终止而不重试 |

### 后果

| 正面 | 负面 |
|---|---|
| §六 的「网络错误可重试」从空头承诺变成真实分支 | 码表 39 → 41，`EXPECT_TOTAL`/`EXPECT_SEG` 与所有引用「39 条」的文档 MUST 同步 |
| 运维看到 3099 就知道该查自己的代码，不必再怀疑上游 | `ToPayload` 的判定顺序成为契约的一部分，改错顺序会造成静默误分类，MUST 有测试逐条覆盖 4 个分支 |
| 熔断不再被本地拥塞误触发 | 2998 的 `details.cause` 需要上游客户端在包装错误时如实填写，漏填会退化成「未知网络错误」 |
| 2999 语义收窄后可安全用于「上游契约变更」告警 | — |

### 重新考虑的条件

- 上游开始返回可解析的网络层错误码（例如网关自报 502/503 而非直接断连）→ 2998 的覆盖面会自然缩小，但**MUST NOT 删除**（本机 DNS/出网故障与上游无关）
- 需要区分「我方可重试的网络抖动」与「上游持续不可达」以驱动不同的退避策略 → 在 `details.cause` 上加权重，而不是拆码
- 引入 Key 池（ADR-008 的阶段二）→ `2402` 的处置会连带影响 2998 的重试判定，届时重审 §六

> 触点：`14-错误契约`（§1.2/§1.3/§2.2/§2.4/§六/§6.1/§七 已改）、`Task-02`（`CodeRegistry` 长度、`ToPayload` 判定顺序、`UpstreamError.Cause`）、`Task-05`（`do()` 包装 `net.Error` 为 2998 并填 `cause`/`attempt`）、`Task-06`（`Breaker.Record` 按 §6.1 收紧、`Retrier.Should` 认 2998）、`Task-10`（`Resources/error-codes.md` 生成 41 条）、`21-测试规范`（「15 个 2xxx」→ 14 个）、`Scripts/CheckConsistency.py`（`EXPECT_TOTAL=41`、`EXPECT_SEG={"1":11,"2":14,"3":16}` 已改）。

## ADR-017 规模红线对存量代码采用「基线棘轮」（冻结存量、只减不增）

**状态**：已接受（2026-10-21）

### 背景

Task-11 A-03 第一次把 `F-S1~F-S5` 从文档承诺变成可执行护栏。实测结果：

| 红线 | 存量违规 |
|---|---|
| F-S1 单文件 ≤600 行 | 0 |
| F-S2 单函数 ≤50 行 | 5 个函数（最大 72 行） |
| F-S3 圈复杂度 ≤10 | 20 个函数（最大 20） |
| F-S4 嵌套 ≤3 | 1 处（`tomlLineIndex`，config 包，已当场修复） |
| F-S5 单包 | `config` 33 / `logging` 38 / `resilience` 50 个导出符号（上限 20）；`tools` 12 文件（上限 10） |

此前这些红线**从未被执行**：`CheckSize.sh` 不存在，`20-编码规范` §1.1 又关掉了 `funlen`/`gocognit`/`gocyclo`。现在只有三种走法：

1. 一次性重构 29 处；
2. 逐条写进豁免台账；
3. 把红线改成迁就现状。

第 2 条违反台账 E5（每个窗口 ≤3 条）；第 3 条让红线对新代码也失效；第 1 条里 F-S5 的导出数是 `Contract/11-接口契约.md` 冻结接口的一部分（如 `resilience` 的 5 个接口与诊断类型），不改契约无法降到 20 —— 在收尾窗口动冻结 API 的回归风险高于收益。

### 决策

采用**基线棘轮（ratchet）**：

- 存量违规写入机器可读基线 `GitHubSrc/Scripts/size-baseline.json`；
- 判定：当前值 > 基线值 ⇒ FAIL；当前值 ≤ 基线值 ⇒ PASS；
- 基线里不存在的函数/文件/包 ⇒ 按原阈值判定，超标即 FAIL；
- 基线只允许减小或删除，MUST NOT 新增条目或调大数值；
- 新代码 MUST 从第一天起达标。

### 放弃的选项

| 选项 | 为什么不选 |
|---|---|
| 一次性重构全部 29 处 | F-S5 导出数受冻结契约约束，不改 `Contract/11-接口契约.md` 无法达标；且与 Task-12~14 交叉，回归风险高 |
| 全部登记豁免台账 | 违反 E5「每个窗口 ≤3 条」，等于废掉豁免制度 |
| 放宽 F-S3/F-S5 阈值 | 红线对新代码也一起失效，问题只是被藏起来 |
| 只让 F-S1 阻断，其余警告 | 本轮「让六条红线有牙齿」的目标落空 |

### 后果

| 正面 | 负面 |
|---|---|
| 六条红线从今天起真正可执行：新代码超标立即可见 | 存量债被显式承认并写入基线，不再假装代码已达标 |
| 不触碰 `Contract/11-接口契约.md` 的冻结导出面 | 基线需要人工维护（只能减不能增） |
| 每清一项债务就删一个基线 key，进度可量化 | `size-baseline.json` 会成为阶段二的前置清理项 |

### 退出条件

`DEBT-010` 清零：删除 `size-baseline.json`，`make size` 与六个守护测试在**无基线、无豁免**的情况下全绿。届时本 ADR 与 AGENTS §7 的「只减不增」注记一并删除。
